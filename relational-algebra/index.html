01Start here

Before SQL existed, there was relational algebra: a small set of operators that take tables in and give tables out. Every SQL query you run is turned into an algebra expression inside the database, and that expression is what the optimizer rewrites to make your query fast. Learning it makes SQL easier to reason about, because you can see what each clause does to the data.

Three ideas to hold on to

  • Closure. Every operator takes relations and returns a relation. That is why operators can be nested as deeply as you like.
  • Sets, not bags. A relation in the textbook model is a set of tuples: no duplicate rows and no row order. SQL tables are bags (duplicates allowed), so to match algebra in SQL you often need DISTINCT. You will see this difference in section 2.
  • Two ways to ask. Relational algebra says how to compute the answer, step by step. Relational calculus says what the answer must satisfy, like a logic statement. Section 9 shows they can express exactly the same queries.

Notation, and how to type it

Textbooks write operator conditions as subscripts, for example σmajor='CS'(Student). Subscripts are awkward to type, so this tutorial writes the condition in square brackets: σ[major="CS"](Student). Brackets

The binary operators (∪ ∩ − × ⋈ ÷) all have the same priority and are applied from left to right. Always use brackets when you mix them, exactly as you would in arithmetic with unusual operators.

02Select, project, rename

Three unary operators do most of the everyday work: σ chooses rows, π chooses columns, and ρ changes names.

Select (σ): keep the rows that satisfy a condition

σ[condition](R) returns the tuples of R for which the condition is true. The result has the same attributes as R. It is the WHERE clause of SQL.

Relational algebra
σ[major="CS" AND gpa >= 3.5](Student)

SQL
SELECT * FROM Student WHERE major = 'CS' AND gpa >= 3.5;
Output (MySQL 8.4)
+-----+-------+-------+------+
| sid | sname | major | gpa  |
+-----+-------+-------+------+
|   1 | Ana   | CS    | 3.80 |
+-----+-------+-------+------+
1 row in set

Checked. The algebra engine on this page and MySQL returned the same 1 row.

Project (π): keep only some columns

π[a, b](R) keeps the listed attributes and then removes duplicate rows, because the result is a set. In SQL that second step is DISTINCT; without it MySQL keeps one output row per input row.

Relational algebra
π[major](Student)

SQL
SELECT DISTINCT major FROM Student;
Output (MySQL 8.4)
+-------+
| major |
+-------+
| CS    |
| MATH  |
| DS    |
+-------+
3 rows in set

Checked. The algebra engine on this page and MySQL returned the same 3 rows.

Plain SELECT without DISTINCT is a bag query, and gives a different answer:

SQL
SELECT major FROM Student;
Output (MySQL 8.4)
+-------+
| major |
+-------+
| CS    |
| CS    |
| MATH  |
| MATH  |
| DS    |
| DS    |
| CS    |
+-------+
7 rows in set

Seven rows instead of three. This is the single most common reason a correct-looking algebra answer and a SQL answer differ by a few rows.

Combine them

Because every operator returns a relation, you can nest them. Read the expression from the inside out: first σ filters the rows, then π keeps the column you want.

Relational algebra
π[sname, gpa](σ[gpa >= 3.5](Student))

SQL
SELECT DISTINCT sname, gpa FROM Student WHERE gpa >= 3.5;
Output (MySQL 8.4)
+-------+------+
| sname | gpa  |
+-------+------+
| Ana   | 3.80 |
| Cara  | 3.90 |
| Eli   | 3.50 |
+-------+------+
3 rows in set

Checked. The algebra engine on this page and MySQL returned the same 3 rows.

The order matters. If you project first, the columns you dropped are gone and a later σ cannot use them:

Relational algebra
σ[gpa >= 3.5](π[sname](Student))

03Union, intersection, difference

Relations are sets, so we can take unions, intersections and differences. These operators need the two inputs to be union-compatible: the same number of attributes, with matching types in each position.

Union (∪)

R ∪ S contains every tuple that is in R, in S, or in both. Example: students enrolled in C1 or C3.

Relational algebra
π[sid](σ[cid="C1"](Enrolled)) ∪ π[sid](σ[cid="C3"](Enrolled))

SQL
SELECT sid FROM Enrolled WHERE cid = 'C1'
UNION
SELECT sid FROM Enrolled WHERE cid = 'C3';
Output (MySQL 8.4)
+-----+
| sid |
+-----+
|   1 |
|   2 |
|   5 |
|   3 |
|   4 |
+-----+
5 rows in set

Checked. The algebra engine on this page and MySQL returned the same 5 rows.

UNION removes duplicates, matching the set operator. UNION ALL keeps them. The result takes its attribute names from the left operand, so you can even union columns that have different names:

Relational algebra
π[sname](Student) ∪ π[iname](Instructor)

SQL
SELECT sname FROM Student UNION SELECT iname FROM Instructor;
Output (MySQL 8.4)
+--------+
| sname  |
+--------+
| Ana    |
| Ben    |
| Cara   |
| Dan    |
| Eli    |
| Fay    |
| Gus    |
| Okafor |
| Tanaka |
| Brooks |
| Romero |
+--------+
11 rows in set

Intersection (∩)

R ∩ S contains the tuples that are in both. Example: students enrolled in C1 and C2.

Relational algebra
π[sid](σ[cid="C1"](Enrolled)) ∩ π[sid](σ[cid="C2"](Enrolled))

SQL
SELECT sid FROM Enrolled WHERE cid = 'C1'
INTERSECT
SELECT sid FROM Enrolled WHERE cid = 'C2';
Output (MySQL 8.4)
+-----+
| sid |
+-----+
|   1 |
|   2 |
+-----+
2 rows in set

Checked. The algebra engine on this page and MySQL returned the same 2 rows.

MySQL version note

INTERSECT and EXCEPT were added to MySQL in version 8.0.31, so they work in MySQL 8.4. Older tutorials say MySQL has no intersect; before 8.0.31 you wrote it with a join or IN. PostgreSQL and SQLite have supported both for many years.

Difference (−)

R − S contains the tuples that are in R but not in S. Order matters: R − S is not the same as S − R. This is how algebra expresses "not" queries. Example: students with no enrollment at all.

Relational algebra
π[sid](Student) − π[sid](Enrolled)

SQL
SELECT sid FROM Student
EXCEPT
SELECT sid FROM Enrolled;
Output (MySQL 8.4)
+-----+
| sid |
+-----+
|   7 |
+-----+
1 row in set

Checked. The algebra engine on this page and MySQL returned the same 1 row.

Only Gus (sid 7) is left. Compare the same idea in the other direction, which is empty because every enrollment belongs to a real student (that is what the foreign key guarantees):

Relational algebra
π[sid](Enrolled) − π[sid](Student)

SQL
SELECT sid FROM Enrolled EXCEPT SELECT sid FROM Student;
Output (MySQL 8.4)
Empty set

Checked. The algebra engine on this page and MySQL returned the same 0 rows.

Intersection is not a new idea

Intersection can be written with difference: R ∩ S = R − (R − S). The engine confirms it on real data:

Relational algebra
π[sid](σ[cid="C1"](Enrolled)) − (π[sid](σ[cid="C1"](Enrolled)) − π[sid](σ[cid="C2"](Enrolled)))

Checked. The algebra engine on this page and MySQL returned the same 2 rows.

That is why textbooks call σ, π, ρ, ∪, − and × the fundamental operators: the others (∩, ⋈, ÷) can be built from them. They exist for convenience.

When the inputs are not compatible

Relational algebra
π[sname](Student) ∪ π[sid, sname](Student)
What the lab says
The two relations must have the same number of attributes to use UNION (left has 1, right has 2). Project them to matching attributes first.

SQL gives the same kind of error: "The used SELECT statements have a different number of columns".

04Products and joins

Joins combine tuples from two relations. All of them are built from one idea: pair up every tuple of one relation with every tuple of the other (the Cartesian product), then keep the pairs that make sense.

Cartesian product (×)

R × S pairs every tuple of R with every tuple of S. With 7 students and 6 courses you get 7 × 6 = 42 tuples, most of them meaningless. The product is rarely useful on its own; it is the raw material for joins.

SQL
SELECT COUNT(*) AS pairs FROM Student CROSS JOIN Course;
Output (MySQL 8.4)
+-------+
| pairs |
+-------+
|    42 |
+-------+
1 row in set

If both relations have an attribute with the same name, the product keeps both; you tell them apart with the relation name (Student.sid, Enrolled.sid).

Theta join (⋈θ): product followed by select

A join with a condition is shorthand: R ⋈[cond] S = σ[cond](R × S). The two forms below are the same query, and the engine confirms they give the same rows. The condition Student.sid = Enrolled.sid is what makes the pairs meaningful: we keep a student only together with their own enrollments.

Relational algebra
σ[Student.sid = Enrolled.sid](Student × Enrolled)

SQL
SELECT * FROM Student, Enrolled WHERE Student.sid = Enrolled.sid;

Checked. The algebra engine on this page and MySQL returned the same 15 rows.

Relational algebra
Student ⋈ [Student.sid = Enrolled.sid] Enrolled

SQL
SELECT * FROM Student JOIN Enrolled ON Student.sid = Enrolled.sid;

Checked. The algebra engine on this page and MySQL returned the same 15 rows.

When the condition is an equality, it is called an equi-join. Both results above have seven columns, and the join column sid appears twice, once from each side. The natural join removes that repetition.

Natural join (⋈): match on the attributes with the same name

R ⋈ S automatically joins on all attributes that have the same name in both relations and keeps one copy of each. Student ⋈ Enrolled matches on sid.

Relational algebra
π[sname, cid, grade](Student ⋈ Enrolled)

SQL
SELECT sname, cid, grade FROM Student NATURAL JOIN Enrolled;
Output (MySQL 8.4)

Common mistake

Natural joins can surprise you. They join on every same-named attribute, and if there are none they silently become a Cartesian product. Student and Course share no attribute name, so this returns 42 tuples, not a useful answer:

Relational algebra
Student ⋈ Course

SQL
SELECT * FROM Student NATURAL JOIN Course;

Checked. The algebra engine on this page and MySQL returned the same 42 rows.

For this reason many SQL teachers prefer JOIN ... ON, which states the matching condition explicitly. A later schema change that adds a same-named column can silently change a natural join's meaning.

Joining a relation with itself

05Division

Division answers "for all" questions: which students have taken every course in this list? It is the least common operator, and the one students find hardest, so we build it up carefully.

The idea

Let R have attributes (A, B) and S have attribute B. Then R ÷ S is the set of A-values a such that for every tuple b in S, the pair (a, b) is in R. The result has the attributes of R that are not in S.

Here R is "which student took which course" and S is a list of required courses. Then R ÷ S is the set of students who took all the required courses.

Division stepper

Choose a set of required courses. The table shows, for every student, which of the required courses they have taken. A student is in the answer only if every required course has a tick.

In algebra and in SQL

Students enrolled in every 4-credit course (C2 and C3):

Relational algebra
π[sid, cid](Enrolled) ÷ π[cid](σ[credits=4](Course))

SQL
SELECT DISTINCT e.sid
FROM Enrolled e
WHERE NOT EXISTS (
  SELECT 1 FROM Course c
  WHERE c.credits = 4
    AND NOT EXISTS (
      SELECT 1 FROM Enrolled x WHERE x.sid = e.sid AND x.cid = c.cid));
Output (MySQL 8.4)
+-----+
| sid |
+-----+
|   1 |
|   3 |
+-----+
2 rows in set

Checked. The algebra engine on this page and MySQL returned the same 2 rows.

SQL has no division operator. The standard translation says "there is no required course for which there is no enrollment", a double NOT EXISTS. Read it from the inside out. A second common form counts: a student qualifies if the number of required courses they have taken equals the number of required courses.

Relational algebra
π[sid, cid](Enrolled) ÷ π[cid](σ[credits=4](Course))
SQL (counting version)
SELECT e.sid
FROM Enrolled e
JOIN Course c ON c.cid = e.cid AND c.credits = 4
GROUP BY e.sid
HAVING COUNT(DISTINCT e.cid) = (SELECT COUNT(*) FROM Course WHERE credits = 4);
Output (MySQL 8.4)
+-----+
| sid |
+-----+
|   1 |
|   3 |
+-----+
2 rows in set

Checked. The algebra engine on this page and MySQL returned the same 2 rows.

Division from the basic operators

Division is not fundamental. With R(A, B) and S(B):

R ÷ S = πA(R) − πA((πA(R) × S) − R)

In words: build every pairing of every candidate with every required item (πA(R) × S), subtract the pairs that really exist (− R), and what is left are the missing pairs. Any candidate with a missing pair fails, so subtract those candidates from the candidate list. The engine confirms that this long form returns the same students as ÷:

Relational algebra
π[sid](π[sid, cid](Enrolled)) − π[sid]((π[sid](π[sid, cid](Enrolled)) × π[cid](σ[credits=4](Course))) − π[sid, cid](Enrolled))

Checked. The algebra engine on this page and MySQL returned the same 2 rows.

Edge case

Division by an empty set. If nobody has to satisfy anything, everybody qualifies. Pick "An empty set" in the stepper: all six students who have at least one enrollment are returned. SQL's double NOT EXISTS behaves the same way (there are no required courses that could be missing). Gus is still absent because he has no tuple in Enrolled at all, so he is not a candidate.

06Grouping and aggregates

The original algebra only reshapes data. Real queries also summarize it: counts, sums, averages. Textbooks add one extension operator, γ (grouping and aggregation), which is the algebra behind GROUP BY. Some books use a different symbol for it (for example a script F), so check yours.

Syntax

γ[grouping attributes ; aggregate AS name, ...](R) splits R into groups that share the same grouping attributes, and then produces one tuple per group. Write the semicolon even when there are no grouping attributes. The aggregates are COUNT, SUM, AVG, MIN and MAX.

Whole-relation aggregates

With nothing before the semicolon there is a single group: the whole relation. Look at what happens to NULL. Fay's GPA is NULL, so AVG(gpa) averages the six known GPAs (20.2 / 6), and COUNT(gpa) counts 6, while COUNT(*) counts all 7 tuples:

Relational algebra
γ[; COUNT(*) AS total, COUNT(gpa) AS with_gpa, AVG(gpa) AS avg_gpa](Student)

SQL
SELECT COUNT(*) AS total, COUNT(gpa) AS with_gpa, ROUND(AVG(gpa), 4) AS avg_gpa FROM Student;
Output (MySQL 8.4)
+-------+----------+---------+
| total | with_gpa | avg_gpa |
+-------+----------+---------+
|     7 |        6 |  3.3667 |
+-------+----------+---------+
1 row in set

Checked. The algebra engine on this page and MySQL returned the same 1 row.

Aggregate functions ignore NULL values, except COUNT(*), which counts tuples.

What algebra cannot do

Even with γ, relational algebra cannot express every question. The classic example is transitive closure, such as "all the prerequisites of a course, however deep the chain". Recursion is needed for that, and SQL provides it as WITH RECURSIVE, which you can try in Module 4.

08Query trees and optimization

Many different algebra expressions return exactly the same answer, but they do not cost the same. A database turns your SQL into an algebra tree and then rewrites the tree into an equivalent, cheaper one before running it.

A query tree

Each operator is a node, base relations are the leaves, and data flows upward. The lab in section 7 shows these trees with the number of tuples at every node. The cost of a plan is driven largely by how many tuples flow through the tree, so an optimizer tries to make the intermediate results small as early as possible.

Rewriting rules that keep the answer the same

  • Push selections down. Filter before you join. σ[cond on R](R ⋈ S) = (σ[cond](R)) ⋈ S when the condition mentions only attributes of R.
  • Push projections down. Drop columns you do not need as early as you can (but keep the join attributes until the join has used them).
  • Replace σ over × by a join. σ[R.a = S.b](R × S) = R ⋈[R.a = S.b] S, which a database can execute without ever building the product.
  • Order the joins. Join order does not change the answer (joins are associative), but it changes the size of the intermediate results.

Compare two plans

Each pair below computes the same answer. The numbers count every tuple that flows through every node of the tree except the final result, including the tuples read from the base relations. Smaller is cheaper. On this toy data the differences are small; on tables with millions of rows they become the difference between a second and an hour.

What MySQL really does

You write the what; the optimizer picks the how. Here is one SQL query that joins in the order Student, Enrolled, Course. MySQL does not run it in that order. It chooses its own plan from statistics about the tables. You will learn to read this output properly in Module 9.

SQL
EXPLAIN FORMAT=TREE SELECT s.sname FROM Student s JOIN Enrolled e ON e.sid = s.sid JOIN Course c ON c.cid = e.cid WHERE c.title = 'Databases'\G

09Tuple relational calculus

Relational calculus describes the answer instead of the steps. Instead of "join, then filter, then project" you write a condition and say: the set of all tuples that make it true. This is much closer to how SQL reads, and to formal logic.

Tuple relational calculus (TRC)

A TRC query has the form { t | P(t) }: the set of tuples t for which the formula P is true. A tuple variable ranges over the tuples of a relation. In this tutorial's typed syntax:

  • s IN Student says the variable s is a tuple of Student. This is called a range atom.
  • s.major = "CS" compares an attribute with a constant, or with another tuple's attribute (e.sid = s.sid).
  • Formulas combine with AND, OR and NOT.
  • EXISTS e IN Enrolled ( ... ) (∃) means some tuple of Enrolled makes the formula true. FORALL c IN Course ( ... ) (∀) means every tuple of Course does.
  • The part before the bar says which attributes to output, written variable.attribute.

Textbooks write the same queries with the symbols ∃, ∀, ∧, ∨ and ¬, and with the range as Student(s) or s ∈ Student. The lab accepts ∃ ∀ ∧ ∨ ¬ ∈ as well as the words.

The pattern for "for all"

The ∀ query above has a shape worth memorizing. "Every CS course is taken by s" is not "for all courses, s took it", because that would include the non-CS courses. You write an implication: for every course, either it is not a CS course, or s took it. In logic that is NOT p OR q. A useful equivalence is ∀x P(x) = ¬∃x ¬P(x), which is exactly why SQL uses a double NOT EXISTS.

Safe expressions

Calculus lets you write formulas that describe infinitely many tuples, such as "all tuples that are not in Student". That is not a database query, because the answer cannot be listed. A safe expression only produces values that appear in the database. Requiring a range atom for every output variable, as this lab does, is one simple way to stay safe.

Domain relational calculus

The other flavour, domain relational calculus, uses variables that range over single attribute values instead of whole tuples, for example { <n> | ∃s,m,g (<s,n,m,g> ∈ Student ∧ m = "CS") }. Query-by-Example (QBE), the fill-in-the-grid query style, is based on it.

Algebra and calculus have the same power

Codd's theorem (1972) says that relational algebra and safe relational calculus can express exactly the same queries. A query language that can express everything in relational algebra is called relationally complete. SQL is relationally complete and adds extras on top (grouping, ordering, recursion, NULLs, duplicates). Informally: calculus is how you think about a query, algebra is how a database executes it, and SQL lets you write either way.
