1. Functional dependencies

Read a schema and say which attributes determine which others, then compute closures and keys from those dependencies.

Theory

What a functional dependency says

A functional dependency (FD) X → Y says: whenever two rows have the same values for X, they must have the same values for Y. We say X determines Y.

  • sid → sname: a student ID always comes with the same name.
  • sid, cid → grade: a grade is fixed by the student and the course together.
  • sid → grade is false: one student has different grades in different courses.
FDs come from the business rules, not from the data. A table with six rows can satisfy an FD by accident. The data can disprove a dependency (one counterexample is enough) but it can never prove one. You decide an FD is real by asking "could this ever have two values?" in the real world.

A dependency is trivial when the right side is already inside the left side (A, B → A). Trivial FDs are always true and never interesting.

Picture

Reading a dependency diagram

Boxes are attributes; the shaded boxes are the key. Each line starts with dots under the determinant and ends with arrowheads on the attributes it determines. Hover or focus a row in the legend to isolate its arrows.

Theory

Deriving new dependencies: Armstrong's axioms

Given a set F of FDs, more follow logically. Three rules generate all of them (they are sound and complete):

RuleStatementExample
ReflexivityIf Y ⊆ X then X → YA, B → A
AugmentationIf X → Y then XZ → YZA → B gives A, C → B, C
TransitivityIf X → Y and Y → Z then X → Zsid → zip and zip → city give sid → city

Handy consequences: union (X → Y and X → Z give X → YZ), decomposition (X → YZ gives X → Y and X → Z), and pseudotransitivity (X → Y and WY → Z give WX → Z).

Theory

Closure: the tool you will use constantly

The closure X⁺ is the set of every attribute that X determines under F. Algorithm: start with X; repeat "if the left side of some FD is inside the set, add its right side" until nothing changes.

Worked example. R(A, B, C, D), F = {A → B, B → C}. Compute A⁺: start {A}; A → B adds B → {A, B}; B → C adds C → {A, B, C}. D never appears, so A⁺ = {A, B, C}.

Closure answers almost every question: X → Y follows from F exactly when Y ⊆ X⁺. And it defines keys:

  • A superkey is a set whose closure is every attribute of R.
  • A candidate key is a minimal superkey (remove any attribute and it stops being one).
  • A prime attribute belongs to at least one candidate key; the rest are non-prime.
Shortcut for finding keys. An attribute that never appears on any right-hand side must be in every key. An attribute that appears only on right-hand sides is in no key. Start from the "must" attributes, check their closure, and add more only if needed.
Theory

Minimal cover: the tidy version of F

A minimal cover is an equivalent set of FDs with no waste. Build it in three steps: (1) make every right side a single attribute; (2) remove extraneous attributes from left sides (in A, B → C, B is extraneous if A → C already follows); (3) remove redundant FDs that the others already imply. You need it for the 3NF synthesis algorithm in module 3.

  cid     TEXT,
  ctitle  TEXT,
  credits INTEGER,
  grade   TEXT

INSERT INTO enroll VALUES
  (1, 'Ada',   'CS101', 'Intro to Programming', 3, 'A'),
  (1, 'Ada',   'CS220', 'Data Structures',      4, 'B'),
  (2, 'Ben',   'CS101', 'Intro to Programming', 3, 'A'),

-- Each number counts the X values that break the dependency (0 means it holds).

       (SELECT COUNT(*) FROM (SELECT 1 FROM enroll GROUP BY sid HAVING COUNT(DISTINCT sname) > 1)) AS violators
UNION ALL SELECT 'cid -> ctitle',
       (SELECT COUNT(*) FROM (SELECT 1 FROM enroll GROUP BY cid HAVING COUNT(DISTINCT ctitle) > 1))
UNION ALL SELECT 'sid, cid -> grade',
       (SELECT COUNT(*) FROM (SELECT 1 FROM enroll GROUP BY sid, cid HAVING COUNT(DISTINCT grade) > 1))
UNION ALL SELECT 'sid -> grade',
       (SELECT COUNT(*) FROM (SELECT 1 FROM enroll GROUP BY sid HAVING COUNT(DISTINCT grade) > 1))
UNION ALL SELECT 'credits -> ctitle',
       (SELECT COUNT(*) FROM (SELECT 1 FROM enroll GROUP BY credits HAVING COUNT(DISTINCT ctitle) > 1))
UNION ALL SELECT 'sname -> sid',
       (SELECT COUNT(*) FROM (SELECT 1 FROM enroll GROUP BY sname HAVING COUNT(DISTINCT sid) > 1));

2. Normal forms: 1NF to BCNF

Take a messy table through each normal form, and know exactly which dependency each step removes.

Theory

Why bother: the three anomalies

When one row records several independent facts, the same fact is stored many times. That causes:

  • Update anomaly: change a customer's city in one row and forget the others, and the table contradicts itself.
  • Insertion anomaly: you cannot record a new product until someone orders it.
  • Deletion anomaly: deleting a customer's last order also erases the customer's address.

Normal forms are a ladder of rules, each one eliminating a kind of dependency that causes these anomalies.

Picture

Three kinds of dependency

This is the same ORDER_LINE table as the top of the page, now colored by what each dependency is doing relative to the key (order_id, product_id).

Theory

The ladder

FormRuleRemoves
1NFEvery cell holds one atomic value; no repeating groups; the table has a primary key.Lists packed into cells
2NF1NF, and every non-prime attribute depends on the whole of every candidate key.Partial dependencies (only matter when a key has 2+ attributes)
3NF2NF, and for every non-trivial FD X → A: X is a superkey or A is a prime attribute.Transitive dependencies through a non-key
BCNFFor every non-trivial FD X → A: X is a superkey. No exceptions.Dependencies whose determinant is not a key, even onto prime attributes
The memory line: every non-key attribute must depend on the key (1NF), the whole key (2NF), and nothing but the key (3NF). BCNF adds: "so help me Codd", every determinant must be a key. Every BCNF table is in 3NF, every 3NF table is in 2NF, and so on.

Theory

When 3NF is not enough: BCNF

Tutoring(student, subject, tutor). Rules: a student has one tutor per subject (student, subject → tutor), and each tutor teaches exactly one subject (tutor → subject). The candidate keys are (student, subject) and (student, tutor). Every attribute is prime, so the table is in 3NF. But tutor is not a key, so it is not in BCNF, and the fact "Lee teaches Math" is stored once per student.

-- ===== Start: items packed into one cell (not 1NF) =====
CREATE TABLE orders_raw (
  order_id INTEGER PRIMARY KEY, order_date TEXT, cust_id TEXT, cust_name TEXT,

);
INSERT INTO orders_raw VALUES
  (1001, '2026-09-01', 'C1', 'Ada',   '20740', 'College Park', 'P10:Pen:1.50:3; P20:Notebook:4.00:1'),
  (1002, '2026-09-02', 'C2', 'Ben',   '20740', 'College Park', 'P10:Pen:1.50:2; P40:Pencil:0.50:10'),

  order_id INTEGER, order_date TEXT, cust_id TEXT, cust_name TEXT,
  postal_code TEXT, city TEXT,
  product_id TEXT, product_name TEXT, unit_price REAL, qty INTEGER,
  PRIMARY KEY (order_id, product_id)
);
INSERT INTO order_line_1nf VALUES
  (1001, '2026-09-01', 'C1', 'Ada',   '20740', 'College Park', 'P10', 'Pen',      1.50,  3),
  (1001, '2026-09-01', 'C1', 'Ada',   '20740', 'College Park', 'P20', 'Notebook', 4.00,  1),
  (1002, '2026-09-02', 'C2', 'Ben',   '20740', 'College Park', 'P10', 'Pen',      1.50,  2),

-- ===== 2NF: remove partial dependencies =====
--   order_id -> order_date, cust_id, ...   (part of the key)
--   product_id -> product_name, unit_price (part of the key)
CREATE TABLE product (
  product_id TEXT PRIMARY KEY, product_name TEXT NOT NULL, unit_price REAL NOT NULL
);
CREATE TABLE orders_2nf (
  order_id INTEGER PRIMARY KEY, order_date TEXT NOT NULL, cust_id TEXT NOT NULL,
  cust_name TEXT NOT NULL, postal_code TEXT NOT NULL, city TEXT NOT NULL
);
CREATE TABLE order_line_2nf (
  order_id   INTEGER REFERENCES orders_2nf(order_id),
  product_id TEXT    REFERENCES product(product_id),
  qty        INTEGER NOT NULL,
  PRIMARY KEY (order_id, product_id)
);
INSERT INTO product        SELECT DISTINCT product_id, product_name, unit_price FROM order_line_1nf;
INSERT INTO orders_2nf     SELECT DISTINCT order_id, order_date, cust_id, cust_name, postal_code, city FROM order_line_1nf;
INSERT INTO order_line_2nf SELECT order_id, product_id, qty FROM order_line_1nf;

-- ===== 3NF: remove transitive dependencies =====
--   order_id -> cust_id -> cust_name, postal_code        postal_code -> city
CREATE TABLE postal (
  postal_code TEXT PRIMARY KEY, city TEXT NOT NULL
);
CREATE TABLE customer (
  cust_id TEXT PRIMARY KEY, cust_name TEXT NOT NULL,
  postal_code TEXT NOT NULL REFERENCES postal(postal_code)
);
CREATE TABLE orders (
  order_id INTEGER PRIMARY KEY, order_date TEXT NOT NULL,
  cust_id TEXT NOT NULL REFERENCES customer(cust_id)
);
CREATE TABLE order_line (
  order_id   INTEGER REFERENCES orders(order_id),
  product_id TEXT    REFERENCES product(product_id),
  qty        INTEGER NOT NULL,
  PRIMARY KEY (order_id, product_id)
);
INSERT INTO postal     SELECT DISTINCT postal_code, city FROM orders_2nf;
INSERT INTO customer   SELECT DISTINCT cust_id, cust_name, postal_code FROM orders_2nf;
INSERT INTO orders     SELECT order_id, order_date, cust_id FROM orders_2nf;
INSERT INTO order_line SELECT order_id, product_id, qty FROM order_line_2nf;

-- The 2NF tables were stepping stones; remove them.
DROP TABLE order_line_2nf;
DROP TABLE orders_2nf;

-- ===== Prove nothing was lost or invented: join everything back and compare =====
WITH rebuilt AS (
  SELECT o.order_id, o.order_date, c.cust_id, c.cust_name, c.postal_code, p.city,
         l.product_id, pr.product_name, pr.unit_price, l.qty
  FROM order_line l
  JOIN orders   o  ON o.order_id    = l.order_id
  JOIN customer c  ON c.cust_id     = o.cust_id
  JOIN postal   p  ON p.postal_code = c.postal_code
  JOIN product  pr ON pr.product_id = l.product_id
)
SELECT (SELECT COUNT(*) FROM (SELECT * FROM order_line_1nf EXCEPT SELECT * FROM rebuilt)) AS lost_rows,
       (SELECT COUNT(*) FROM (SELECT * FROM rebuilt EXCEPT SELECT * FROM order_line_1nf)) AS invented_rows;

-- The payoff: a fact now lives in ONE place. Rename the city once; both customers see it.
UPDATE postal SET city = 'College Park, MD' WHERE postal_code = '20740';
SELECT c.cust_name, p.city FROM customer c JOIN postal p ON p.postal_code = c.postal_code ORDER BY c.cust_id;

3. Evaluating decompositions

Splitting a table is easy. Splitting it correctly means you can rebuild the original exactly and still enforce every rule.

Theory

Two properties every good decomposition needs

Lossless join. Joining the pieces back together must give exactly the original rows: no row lost, no extra "spurious" row invented. A lossy decomposition fails the second way: the join manufactures combinations that never happened, so you cannot trust any answer.

Dependency preservation. Every FD in F should be checkable inside a single decomposed table (or follow from the FDs that are). If not, enforcing the rule means joining tables on every write.

Lossless join is mandatory. Dependency preservation is desirable, and sometimes you must trade it away.

Theory

Testing for lossless join

Two tables. Decomposing R into R₁ and R₂ is lossless if and only if the shared attributes determine all of one side:

R₁ ∩ R₂ → R₁ − R₂  or  R₁ ∩ R₂ → R₂ − R₁

In plain words: the shared columns must be a key of at least one of the pieces.

Any number of tables: the chase. Build a grid with one row per piece and one column per attribute. Put the symbol a where the piece has the attribute and a unique b symbol where it does not. For each FD X → Y: whenever two rows agree on X, make them agree on Y (replace a b with an a if one is available). Repeat until nothing changes. The decomposition is lossless if some row ends up entirely a.

Theory

Testing dependency preservation

For each FD X → Y in F: start with Z = X. Repeat over every piece Rᵢ: Z = Z ∪ ((Z ∩ Rᵢ)⁺ ∩ Rᵢ), until Z stops growing. If Y ⊆ Z, the FD is preserved. The trick is that you never compute the projected dependencies; closure under the original F does the work.

Theory

Two algorithms that produce good decompositions

BCNF decomposition
  1. Find a table Rᵢ with a violating FD X → Y (X not a superkey of Rᵢ).
  2. Replace Rᵢ with X⁺ ∩ Rᵢ and Rᵢ − (X⁺ − X).
  3. Repeat until every piece is in BCNF.

Guarantees: lossless. Does not guarantee dependency preservation.

3NF synthesis
  1. Compute a minimal cover.
  2. Make one table per left side, containing that left side and everything it determines.
  3. Drop any table contained in another.
  4. If no table contains a candidate key of R, add one that does.

Guarantees: lossless and dependency-preserving, every table in 3NF.

3NF synthesisBCNF decomposition
Lossless joinAlwaysAlways
Dependency preservingAlwaysNot always
Redundancy from FDsA little can remainNone

Practical rule: aim for BCNF. If it costs you a dependency you cannot afford to lose, settle for 3NF and say why.

Lab 3: lossless join and dependency preservation
PRAGMA foreign_keys = OFF;
DROP TRIGGER IF EXISTS one_tutor_per_subject;
DROP TABLE IF EXISTS student_tutor;  DROP TABLE IF EXISTS tutor_subject;  DROP TABLE IF EXISTS tutoring;
DROP TABLE IF EXISTS guest_hotel;    DROP TABLE IF EXISTS hotel_loc;
DROP TABLE IF EXISTS guest_city;     DROP TABLE IF EXISTS hotel_city;     DROP TABLE IF EXISTS booking;
PRAGMA foreign_keys = ON;

-- ===== Part A: lossless join =====
-- Booking(guest, hotel, city) with hotel -> city. Key: (guest, hotel).
CREATE TABLE booking (guest TEXT, hotel TEXT, city TEXT, PRIMARY KEY (guest, hotel));
INSERT INTO booking VALUES
  ('Ada', 'Hilton',   'Boston'),
  ('Ben', 'Marriott', 'Boston'),
  ('Ada', 'Ritz',     'Paris');

-- BAD decomposition: split on city. city determines neither guest nor hotel.
CREATE TABLE guest_city AS SELECT DISTINCT guest, city FROM booking;
CREATE TABLE hotel_city AS SELECT DISTINCT hotel, city FROM booking;

SELECT g.guest, h.hotel, g.city
FROM guest_city g JOIN hotel_city h ON h.city = g.city
ORDER BY g.guest, h.hotel;

-- The extra rows are "spurious tuples": combinations that were never in the original.
SELECT g.guest, h.hotel, g.city
FROM guest_city g JOIN hotel_city h ON h.city = g.city
EXCEPT
SELECT guest, hotel, city FROM booking
ORDER BY 1, 2;

-- GOOD decomposition: split on hotel. hotel -> city, so hotel is a key of hotel_loc.
CREATE TABLE hotel_loc (hotel TEXT PRIMARY KEY, city TEXT NOT NULL);
CREATE TABLE guest_hotel (
  guest TEXT, hotel TEXT REFERENCES hotel_loc(hotel),
  PRIMARY KEY (guest, hotel)
);
INSERT INTO hotel_loc   SELECT DISTINCT hotel, city FROM booking;
INSERT INTO guest_hotel SELECT guest, hotel FROM booking;

SELECT (SELECT COUNT(*) FROM (
          SELECT gh.guest, gh.hotel, hl.city FROM guest_hotel gh JOIN hotel_loc hl ON hl.hotel = gh.hotel
          EXCEPT SELECT guest, hotel, city FROM booking)) AS spurious_rows,
       (SELECT COUNT(*) FROM (
          SELECT guest, hotel, city FROM booking
          EXCEPT
          SELECT gh.guest, gh.hotel, hl.city FROM guest_hotel gh JOIN hotel_loc hl ON hl.hotel = gh.hotel)) AS lost_rows;

-- ===== Part B: dependency preservation =====
-- Tutoring(student, subject, tutor):  student, subject -> tutor   and   tutor -> subject.
-- The BCNF decomposition is lossless, but no single table contains student, subject AND tutor.
CREATE TABLE tutor_subject (tutor TEXT PRIMARY KEY, subject TEXT NOT NULL);
CREATE TABLE student_tutor (
  student TEXT, tutor TEXT REFERENCES tutor_subject(tutor),
  PRIMARY KEY (student, tutor)
);
INSERT INTO tutor_subject VALUES ('Lee', 'Math'), ('Kim', 'Physics'), ('Park', 'Math');
INSERT INTO student_tutor VALUES ('Ada', 'Lee'), ('Ada', 'Kim'), ('Ben', 'Lee');

-- Ada already has a Math tutor (Lee). Park also teaches Math. The database accepts this,
-- even though it breaks the original rule  student, subject -> tutor:
INSERT INTO student_tutor VALUES ('Ada', 'Park');

SELECT st.student, ts.subject, COUNT(DISTINCT st.tutor) AS tutors
FROM student_tutor st JOIN tutor_subject ts ON ts.tutor = st.tutor
GROUP BY st.student, ts.subject
HAVING COUNT(DISTINCT st.tutor) > 1;

-- The lost dependency must now be enforced by hand. Remove the bad row, add a trigger:
DELETE FROM student_tutor WHERE student = 'Ada' AND tutor = 'Park';

CREATE TRIGGER one_tutor_per_subject
BEFORE INSERT ON student_tutor
WHEN EXISTS (
  SELECT 1
  FROM student_tutor st
  JOIN tutor_subject have ON have.tutor = st.tutor
  JOIN tutor_subject want ON want.tutor = NEW.tutor
  WHERE st.student = NEW.student AND have.subject = want.subject
)
BEGIN
  SELECT RAISE(ABORT, 'student already has a tutor for that subject');
END;

4. Normalization versus performance

Normalization buys consistency and costs joins. Learn when that price is worth paying, and how to pay less of it.

Theory

The trade in one table

More normalizedMore denormalized
ReadsMore joins per queryFewer joins, wider rows
WritesOne place to change a factEvery copy must change
ConsistencyEnforced by the structureEnforced by your code, or not at all
StorageSmallerLarger (repeated values)
Changing the schemaLocal and clearTouches many columns

Where each tends to win. Systems that take many small, concurrent updates (orders, payments, enrolments, called OLTP) favor normalization. Read-mostly reporting and analytics (OLAP, data warehouses) often favor wide, pre-joined tables, such as a star schema, loaded from the normalized source on a schedule.

Theory

Before you denormalize

  1. Measure. Find the slow query and its actual plan. Do not guess.
  2. Index. Most "slow join" problems are missing indexes on the join columns.
  3. Rewrite or cache. A better query, a cached result, or a read replica often removes the problem.
  4. Then consider a controlled copy: a precomputed column, a summary table, or a materialized view.

If you do copy data, keep the normalized tables as the source of truth and treat the copy as a cache you can rebuild. Decide how it stays consistent: a trigger, the same transaction in the application, or a scheduled rebuild. Write the decision down.

Not every copy is redundancy. The unit price on an order line is a different fact from the product's current price: it is the price at the time of sale. It can legitimately differ, so it belongs in the order line. Redundancy means storing the same fact twice, not storing a historical snapshot.

-- Normalized: two joins

-- ===== A middle path: keep the base tables normalized, add a summary table kept in sync by a trigger =====
CREATE TABLE customer_revenue (cust_id INTEGER PRIMARY KEY, revenue REAL NOT NULL);
INSERT INTO customer_revenue
SELECT s.cust_id, SUM(s.qty * p.unit_price)
FROM sale s JOIN product p ON p.product_id = s.product_id
GROUP BY s.cust_id;

CREATE TRIGGER sale_after_insert
AFTER INSERT ON sale
BEGIN
  INSERT INTO customer_revenue (cust_id, revenue)
  VALUES (NEW.cust_id, NEW.qty * (SELECT unit_price FROM product WHERE product_id = NEW.product_id))
  ON CONFLICT (cust_id) DO UPDATE SET revenue = revenue + excluded.revenue;
END;

SELECT revenue FROM customer_revenue WHERE cust_id = 7;

INSERT INTO sale VALUES (100001, 7, 5, 3);

-- The summary must always equal the live calculation:
SELECT ROUND(r.revenue, 2) AS summary,
       ROUND((SELECT SUM(s.qty * p.unit_price) FROM sale s JOIN product p ON p.product_id = s.product_id
              WHERE s.cust_id = 7), 2) AS recomputed
FROM customer_revenue r WHERE r.cust_id = 7;
-- This trigger only covers INSERT. A real system also needs UPDATE and DELETE triggers (or a scheduled rebuild).

5. Refining a schema for maintainability and consistency

Take an existing, messy database and improve it safely: find the rules, split the tables, write the rules down as constraints, and migrate without losing a row.

Theory

The refactoring workflow

  1. Audit. List the business rules as FDs. Query the data to find where it already breaks them.
  2. Clean. Fix inconsistent values (spelling, case, whitespace) before splitting, or the split will duplicate them as separate "facts".
  3. Design. Decompose to 3NF or BCNF. Choose keys.
  4. Constrain. Turn every rule into something the database enforces.
  5. Migrate. Copy parents before children with INSERT ... SELECT DISTINCT.
  6. Verify. Prove the new tables reproduce the old data (EXCEPT both ways must return nothing).
  7. Bridge. Publish a view with the old shape so existing queries keep working while you migrate callers.
  8. Retire the old table once nothing reads it.
Theory

The constraint toolbox

ConstraintEnforcesTypical use
PRIMARY KEYEach row is uniquely identifiableEvery table
FOREIGN KEYA reference points at a real row (referential integrity)Every relationship
UNIQUENo duplicates in a column that is not the keyEmail, code, other candidate keys
NOT NULLA value must existTotal participation, required facts
CHECKA value satisfies a ruleqty > 0, small fixed lists of values
Lookup tableAllowed values live in data, not in codeStatuses or categories that change
TriggerRules that span tablesFDs lost in a decomposition (module 3)

Maintainability habits. One table per kind of thing. Each fact has exactly one home. Names say what a column is. Schema changes live in scripts you can rerun, and every migration ends with a reconciliation query.

SELECT cust_id, COUNT(DISTINCT city) AS spellings
FROM legacy_orders GROUP BY cust_id HAVING COUNT(DISTINCT city) > 1;

-- ===== Step 2: clean the data BEFORE splitting (one spelling per city) =====
UPDATE legacy_orders
SET city = UPPER(SUBSTR(TRIM(city), 1, 1)) || LOWER(SUBSTR(TRIM(city), 2));

SELECT cust_id, COUNT(DISTINCT city) AS spellings
FROM legacy_orders GROUP BY cust_id HAVING COUNT(DISTINCT city) > 1;

-- ===== Step 3: create the target schema, with the rules written down as constraints =====
CREATE TABLE city (
  city_id   INTEGER PRIMARY KEY,
  city_name TEXT NOT NULL UNIQUE
);
CREATE TABLE customer (
  cust_id   TEXT PRIMARY KEY,
  cust_name TEXT NOT NULL,
  email     TEXT NOT NULL UNIQUE,
  city_id   INTEGER NOT NULL REFERENCES city(city_id)
);
CREATE TABLE product (
  product_code TEXT PRIMARY KEY,
  product_name TEXT NOT NULL,
  unit_price   REAL NOT NULL CHECK (unit_price >= 0)
);
CREATE TABLE orders (
  order_id   INTEGER PRIMARY KEY,
  order_date TEXT NOT NULL,
  cust_id    TEXT NOT NULL REFERENCES customer(cust_id)
);
CREATE TABLE order_line (
  order_id     INTEGER REFERENCES orders(order_id),
  product_code TEXT    REFERENCES product(product_code),
  qty          INTEGER NOT NULL CHECK (qty > 0),
  PRIMARY KEY (order_id, product_code)
);

-- ===== Step 4: migrate, parents before children =====
INSERT INTO city (city_name) SELECT DISTINCT city FROM legacy_orders ORDER BY city;
INSERT INTO customer
  SELECT DISTINCT l.cust_id, l.cust_name, l.email, c.city_id
  FROM legacy_orders l JOIN city c ON c.city_name = l.city;
INSERT INTO product    SELECT DISTINCT product_code, product_name, unit_price FROM legacy_orders;
INSERT INTO orders     SELECT DISTINCT order_id, order_date, cust_id FROM legacy_orders;
INSERT INTO order_line SELECT order_id, product_code, qty FROM legacy_orders;

-- ===== Step 5: a compatibility view that looks exactly like the old table =====
CREATE VIEW legacy_orders_v AS
SELECT o.order_id, o.order_date, c.cust_id, c.cust_name, c.email, ci.city_name AS city,
       p.product_code, p.product_name, p.unit_price, l.qty
FROM order_line l
JOIN orders   o  ON o.order_id     = l.order_id
JOIN customer c  ON c.cust_id      = o.cust_id
JOIN city     ci ON ci.city_id     = c.city_id
JOIN product  p  ON p.product_code = l.product_code;

-- ===== Step 6: reconcile. Both numbers must be 0 =====
SELECT (SELECT COUNT(*) FROM (SELECT * FROM legacy_orders EXCEPT SELECT * FROM legacy_orders_v)) AS lost_rows,
       (SELECT COUNT(*) FROM (SELECT * FROM legacy_orders_v EXCEPT SELECT * FROM legacy_orders)) AS invented_rows;

-- Old reports keep working through the view:
SELECT city, ROUND(SUM(qty * unit_price), 2) AS revenue FROM legacy_orders_v GROUP BY city ORDER BY city;
