Why one query is instant and another crawls

A database table is a file on a disk, and a disk hands over whole pages at a time. A query is fast when it makes the DBMS read few pages. Everything in this module, from file organizations to B+ trees to composite indexes, is a way of reading fewer of them. Click each layer to see where the pages live.

1. Storage and blocks

Explain how records are packed into blocks, compute how many blocks a table needs, and say why block reads are the unit of cost.

Theory

The disk gives you pages, not rows

Memory is fast and small. Disks are slow and large, and they transfer data in fixed-size units called blocks (the DBMS calls them pages). Typical sizes are 4 KB in SQLite, 8 KB in PostgreSQL, and 16 KB in MySQL's InnoDB. To read one 100-byte row, the DBMS must read the whole page that contains it.

Because moving a page from disk costs far more than comparing values in memory, database designers count block accesses to predict how long a query will take. The count is not exact, but it ranks plans correctly, and the whole module uses it.

A cache sits in between. The DBMS keeps recently used pages in memory, in a buffer pool. A page that is already there costs almost nothing, which is why the second run of a query is often faster. The block-access count is the cost when the cache is cold, and it is still the right way to compare designs.

Packing records into blocks

Suppose a record is R bytes and a block is B bytes. If records may not span two blocks, the blocking factor is how many whole records fit:

bf = ⌊B / R⌋     b = ⌈N / bf⌉

where N is the number of records and b is the number of blocks in the file. The floor matters: a block with room for 20.48 records holds 20, and the leftover bytes are wasted. The ceiling matters too: 500.1 blocks of data need 501 blocks.

Worked example. N = 10,000 records, R = 200 bytes, B = 4,096 bytes. Then bf = ⌊4096 / 200⌋ = ⌊20.48⌋ = 20 and b = ⌈10,000 / 20⌉ = 500 blocks. A full scan reads all 500. Those are exactly the numbers lab 1 uses in the next section.

Theory

The cost model used from here on

  • Cost = number of block accesses (reads and writes). CPU time and the cache are ignored.
  • Records are fixed-length and do not span blocks. Real DBMSs handle variable lengths with a slotted-page layout, but the counting idea is the same.
  • Sequential reads of neighboring blocks are cheaper than random reads of scattered ones. The simple model treats them alike, and later sections point out where the difference changes a decision.

With this, we can ask the central question of the module: for a given kind of query, how few blocks can we get away with reading? Different file organizations answer differently.

2. File organization

Describe heap, sorted, hashed, and indexed files, compare their block-access costs, and pick one for a given access pattern.

Theory

Four ways to arrange records in a file

A file organization decides which block each record goes into. That choice fixes which operations are cheap.

  • Heap (unordered). New records go wherever there is room, usually the end. Inserts are cheap. Finding a record means scanning, on average half the file when it exists and all of it when it does not.
  • Sorted (sequential). Records are kept in order of a key. Binary search over the blocks finds a key in about log₂ b reads, and a range query reads a contiguous run of blocks. Inserts are expensive, because the new record must go in the right place and later records may have to shift.
  • Hashed. A hash function maps the key to a bucket (one or more blocks). An exact-match lookup costs about one read. Neighboring keys land in unrelated buckets, so a range query has to read everything.
  • Indexed. A separate index structure, such as a B+ tree, stores keys with pointers into the data file. It supports both equality and range lookups at near-logarithmic cost, and it copes well with growth. Sections 3 and 4 explain how.

Costs side by side

With b data blocks, bf records per block, and a B+ tree of height h (counted in levels, so one read per level):

OrganizationFind one keyRange of m blocksInsert
Heapb / 2 on average (b if absent)babout 2 (read and write the last block)
Sorted⌈log₂ b⌉⌈log₂ b⌉ + m − 1about b (half the file shifts: read and write)
Hashedabout 1 (more if overflow)b (scan every bucket)about 2
B+ tree indexh + 1h + mabout h + 2, plus an occasional split

No organization wins everywhere. The skill is matching the structure to what the table is asked to do.

"""Count block accesses for three file organizations. A 'block access' is one block read or written."""
import math
import random

random.seed(42)
N = 10_000                       # records
BF = 20                          # blocking factor: records per block
keys = random.sample(range(1, 1_000_000), N)
B = math.ceil(N / BF)            # blocks in the file
print(f"{N:,} records, {BF} per block -> {B} blocks\n")


# ---------------- Heap file: records in arrival order ----------------
class Heap:
    def __init__(self, ks):
        self.blocks = [ks[i:i + BF] for i in range(0, len(ks), BF)]

    def search(self, k):                       # scan until found
        reads = 0
        for blk in self.blocks:
            reads += 1
            if k in blk:
                return reads
        return reads

    def range(self, lo, hi):                   # must read everything
        return len(self.blocks)

    def insert(self, k):                       # read the last block, write it back
        if len(self.blocks[-1]) < BF:
            self.blocks[-1].append(k)
            return 2
        self.blocks.append([k])
        return 1                               # a brand-new block is only written


# ---------------- Sorted (sequential) file ----------------
class Sorted:
    def __init__(self, ks):
        self.keys = sorted(ks)

    def _nblocks(self):
        return math.ceil(len(self.keys) / BF)

    def _block(self, i):
        return self.keys[i * BF:(i + 1) * BF]

    def _find_block(self, k):                  # binary search over blocks; returns (block index, reads)
        lo, hi, reads = 0, self._nblocks() - 1, 0
        while lo <= hi:
            mid = (lo + hi) // 2
            blk = self._block(mid)
            reads += 1
            if k < blk[0]:
                hi = mid - 1
            elif k > blk[-1]:
                lo = mid + 1
            else:
                return mid, reads
        return min(lo, self._nblocks() - 1), reads

    def search(self, k):
        return self._find_block(k)[1]

    def range(self, lo, hi):                   # binary search for the first block, then read forward
        i, reads = self._find_block(lo)
        while i < self._nblocks() - 1 and self._block(i)[-1] < hi:
            i += 1
            reads += 1
        return reads

    def insert(self, k):                       # shift later records: every later block is read and rewritten
        i, reads = self._find_block(k)
        after = self._nblocks() - i
        bisect_pos = sum(1 for x in self.keys if x < k)
        self.keys.insert(bisect_pos, k)
        return reads + 2 * after


# ---------------- Static hash file ----------------
class Hashed:
    def __init__(self, ks, buckets):
        self.m = buckets
        self.chains = [[[]] for _ in range(buckets)]    # each bucket: a chain of blocks
        for k in ks:
            self.insert(k)

    def search(self, k):
        reads = 0
        for blk in self.chains[k % self.m]:
            reads += 1
            if k in blk:
                return reads
        return reads

    def range(self, lo, hi):                   # the hash scatters neighbours: scan every block
        return sum(len(c) for c in self.chains)

    def insert(self, k):
        reads = 0
        chain = self.chains[k % self.m]
        for blk in chain:
            reads += 1
            if len(blk) < BF:
                blk.append(k)
                return reads + 1               # + one write
        chain.append([k])                      # overflow block
        return reads + 1


heap, srt = Heap(keys), Sorted(keys)
hsh = Hashed(keys, buckets=math.ceil(N / (BF * 0.8)))   # sized for 80% full buckets
overflow = sum(len(c) - 1 for c in hsh.chains)
print(f"hash file: {hsh.m} buckets, {overflow} overflow blocks\n")

probe = random.sample(keys, 1000)
sk = sorted(keys)
lo, hi = sk[4000], sk[4199]                    # a range holding exactly 200 records
taken = set(keys)
new_keys = []
while len(new_keys) < 500:
    x = random.randrange(1, 1_000_000)
    if x not in taken:
        taken.add(x)
        new_keys.append(x)

rows = []
for name, f in [("heap (unsorted)", heap), ("sorted", srt), ("hashed", hsh)]:
    eq = sum(f.search(k) for k in probe) / len(probe)
    rg = f.range(lo, hi)
    ins = sum(f.insert(k) for k in new_keys) / len(new_keys)
    rows.append((name, eq, rg, ins))

print(f"{'organization':<18}{'equality search':>17}{'range (200 rows)':>18}{'insert':>9}")
print(f"{'':<18}{'(avg blocks)':>17}{'(blocks)':>18}{'(avg)':>9}")
for name, eq, rg, ins in rows:
    print(f"{name:<18}{eq:>17.1f}{rg:>18}{ins:>9.1f}")
print(f"\nlog2({B}) = {math.log2(B):.1f}   (the sorted file's binary search should land near this)")

What to notice.

  • Heap equality is 244, close to the b / 2 = 250 the formula predicts. Sorted equality is 8.0, near log₂ 500 = 9.
  • Hashed equality is about 1.0 block on average, even though 92 overflow blocks exist: most buckets never overflowed, so most lookups end in the first block.
  • The hashed file's range query reads 717 blocks, more than the 500 of a plain scan, because every bucket and its overflow blocks must be visited.
  • Sorted inserts cost 524 block accesses each: about the whole file. That is the price of keeping order.

Try it. Change BF to 50 and rerun: every count drops. Then change the 0.8 in the line that sizes the hash file to 1.5 (fewer buckets than the records need) and watch the overflow count, the equality cost, and the range cost grow together.

Theory

Hashing in more detail

In static hashing, the file has a fixed number n of buckets and the hash function is something like key mod n. A bucket is one block. When a bucket is full, extra records go into a chain of overflow blocks, and every lookup in that bucket has to walk the chain. Two things hurt: too few buckets (long chains), and a poor hash function or skewed keys (a few overloaded buckets). Growing n is painful, because most keys now hash somewhere else and nearly the whole file must be rewritten.

Interactive

Each box is a block holding up to the chosen number of records. Press Add 5 collisions to insert multiples of the bucket count, which all land in bucket 0. Then change the number of buckets and watch every record get rehashed.

Extendible hashing grows without rehashing everything

Extendible hashing adds a small directory. The directory has 2d entries, where d is the global depth, and entry i points to the bucket that holds keys whose last d bits equal i. Several directory entries can point to the same bucket. Each bucket has a local depth, the number of bits it actually uses.

When a bucket overflows:

  1. If its local depth is less than the global depth, only that bucket splits: its records are divided by the next bit, and the directory pointers are repaired. No doubling.
  2. If its local depth equals the global depth, the directory first doubles (d goes up by one, each pointer is duplicated), and then the bucket splits.

Only the overflowing bucket's records move. A lookup is still one directory access (in memory) and one bucket read. Linear hashing reaches the same goal differently, by splitting buckets in a fixed rotating order.

3. Index structures

Explain what an index is, distinguish primary, clustering, and secondary indexes, dense and sparse, and compute the size and depth of a multilevel index.

Theory

An index is a small sorted shortcut

An index is a separate structure made of entries (search key, pointer), kept in key order. It works like the index at the back of a book: instead of reading every page to find a word, you look the word up in a short sorted list and jump to the page. Because the entries are small (a key and a pointer, not a whole record), the index is far smaller than the data file, so searching it costs far fewer block reads.

A table may have many indexes, each on a different column or combination of columns. Each index is its own file of blocks that the DBMS must keep in step with the table.

Three kinds, by what the file is sorted on

KindIndexed fieldData fileTypical entries
Primary indexThe ordering key of the file (unique)Sorted on that keyOne per block (usually sparse)
Clustering indexThe ordering field, not uniqueSorted on that fieldOne per distinct value
Secondary indexAny other fieldNot sorted on itOne per record (dense)

A file can be sorted in only one way, so it can have at most one primary or clustering index, but any number of secondary indexes.

Vocabulary varies. The terms above are the textbook ones. Database products reuse the word “clustered”: in MySQL's InnoDB the whole table is stored inside a B+ tree on the primary key, called the clustered index, and every other index stores the primary key as its pointer. In PostgreSQL, tables are heaps and every index is secondary. Ask which meaning a source uses.

Dense or sparse

  • A dense index has an entry for every record (every search-key value). It can say whether a key exists without touching the data file.
  • A sparse index has an entry only for some records, typically the first record of each block. It is smaller, but it only works when the data file is sorted on the same field: you find the last entry whose key is ≤ the target, read that block, and scan it.

A secondary index cannot be sparse. Records with neighboring values can be anywhere in the file, so there is no block whose first key describes a range.

Theory

Multilevel indexes: index the index

A big file needs a big index, and searching a big sorted index still takes log₂ of its size. The fix is to treat the index as a file and index it, again and again, until the top level fits in one block. Each level shrinks the problem by a factor equal to the number of entries per block (the fan-out), so lookups cost one read per level plus the data block.

Worked example. 100,000 records of 200 bytes in 4,096-byte blocks: bf = 20, so the data file has 5,000 blocks. An index entry (8-byte key, 8-byte pointer) is 16 bytes, so 256 entries fit per index block.

  • Binary search of the data file itself: ⌈log₂ 5,000⌉ = 13 reads.
  • Sparse primary index, one entry per data block: 5,000 entries need ⌈5,000 / 256⌉ = 20 index blocks. Level two: ⌈20 / 256⌉ = 1 block. Two levels, so a lookup costs 2 + 1 = 3 reads.
  • Dense secondary index, one entry per record: 100,000 entries need ⌈100,000 / 256⌉ = 391 blocks, then 2, then 1. Three levels, so a lookup costs 3 + 1 = 4 reads (and a non-unique value may need more data blocks).

Three or four reads for a hundred thousand records, and the number barely moves if the table grows tenfold. That insight is the whole motivation for the tree structures in the next section: a multilevel index that is static is easy, but one that handles inserts and deletes gracefully needs a different idea.

Multilevel index calculator

The defaults reproduce the worked example. Increase N to 100 million: how many levels does the dense index need now?

Why a static multilevel index is not enough

The indexed-sequential (ISAM) file is exactly this: a sorted data file plus fixed index levels. Inserting a record means making room in a data block, and when the block is full the record goes into an overflow chain. Over time the chains grow and performance decays, until someone rebuilds the file. We want an index that rebalances itself as the data changes. That is what B-trees and B+ trees do.

4. B-trees and B+ trees

Describe the structure of B-trees and B+ trees, compute fan-out and height, and trace search, range scan, insert (with splits), and delete (with borrowing and merging).

Theory

A tree shaped like a disk block

A binary search tree has two children per node. On disk that is a disaster: a million keys need about 20 levels, so about 20 block reads. A B-tree (the B is traditionally read as “balanced”, or for its inventor Bayer) makes each node as big as a block and gives it hundreds of children. The same million keys then fit in 3 levels.

Both B-trees and B+ trees obey the same balance rules, for a node that holds at most m keys:

  • All leaves are at the same depth, so every search costs the same number of reads.
  • Keys in a node are sorted, and the child pointers between them lead to subtrees whose keys fall in the matching ranges.
  • Every node except the root is at least half full. That guarantees a fan-out that is never tiny, so the height stays small.

B-tree versus B+ tree

B-treeB+ tree
Record pointersIn every nodeOnly in leaves
Keys appearOnce in the treeIn a leaf always; copies as separators above
Internal fan-outSmaller (pointers use space)Larger (just key and child pointer)
Leaves linkedNoYes: next-leaf pointers in key order
Range scanNeeds in-order traversal up and downOne descent, then walk the leaf chain
Search costCan stop early at an internal nodeAlways reaches a leaf: the same cost for every key

Almost every database index uses the B+ tree design, even when the documentation just says “B-tree”. The larger fan-out and the leaf chain beat the occasional early exit of a plain B-tree.

Theory

Fan-out and height

Let a block hold B bytes, a key K bytes, a block pointer P bytes, and a record pointer Pr bytes. An internal B+ tree node with n children holds n pointers and n − 1 keys, so it needs n·P + (n − 1)·K ≤ B:

B+ tree: n = ⌊(B + K) / (P + K)⌋     B-tree: n = ⌊(B + K + Pr) / (P + K + Pr)⌋

(In a B-tree each of the n − 1 keys also carries a record pointer, which is why its n is smaller.) A leaf entry is K + Pr bytes, and one pointer is reserved for the next leaf.

Worked example. B = 4,096, K = 8, P = 8, Pr = 8. B+ tree internal fan-out: ⌊4,104 / 16⌋ = 256. B-tree fan-out: ⌊4,112 / 24⌋ = 171. A leaf holds ⌊(4,096 − 8) / 16⌋ = 255 entries.

Real trees are not completely full. After random inserts the average node is about 69% full (the natural logarithm of 2). So a B+ tree typically has about 0.69 × 256 ≈ 176 children per node and 175 entries per leaf. For N keys:

  • Leaves needed: ⌈N / 175⌉. Each level above divides by about 176 until one node remains.
  • 100,000 keys: 572 leaves → 4 nodes → 1 root: 3 levels.
  • 5 million keys: 28,572 leaves → 163 → 1: 3 levels for the B+ tree, but a B-tree with fan-out 171 needs 4.
  • 1 billion keys: still only 5 levels.

Height grows with the logarithm of N, with a base in the hundreds. A table that is 10,000 times larger costs one or two more reads. That is why an indexed lookup on a huge table feels instant.

Theory

The four operations

Search. Start at the root. In each internal node, follow the pointer whose key range contains the target. At the leaf, look for the key. Cost: one read per level.

Range scan. Search for the lower bound. Then walk the next-leaf pointers, collecting keys, until a key exceeds the upper bound. Cost: the descent plus one read per extra leaf, never a trip back to the root.

Insert. Search for the leaf where the key belongs and add it in order. If the leaf now has more than m keys, it splits into two half-full leaves, and the first key of the right leaf is copied up into the parent as a separator. If the parent overflows, it splits too, but its middle key is moved up (it is not kept in either half). If the root splits, a new root is created above it. The tree grows from the top, so all leaves stay at the same depth.

Delete. Search for the leaf and remove the key. If the leaf drops below half full, first try to borrow a key from a sibling that has one to spare (and fix the parent's separator). If neither sibling can spare one, merge the node with a sibling and remove the separator from the parent. The parent may now be underfull, so the same repair can cascade upward, and if the root is left with one child, the tree shrinks by one level.

Each split or merge touches only a few nodes, so insert and delete cost about the same as a search, with an occasional extra write.

A worked example, by hand

Max 3 keys per node. Insert 10, 20, 5, 6, 12, 30, 7, 17, 3, 25, 28, 40, one at a time. Leaves are separated by bars.

  1. Insert 10, 20, 5: one leaf, [5, 10, 20].
  2. Insert 6: the leaf would hold 4 keys, [5, 6, 10, 20]. Split into [5, 6] and [10, 20]. Copy 10 up: a new root [10]. Height 2.
  3. Insert 12 fits in [10, 12, 20]. Insert 30 overflows it: split into [10, 12] and [20, 30], copy 20 up. Root [10, 20].
  4. Insert 7 and 17 fit. Insert 3 overflows [3, 5, 6, 7]: split [3, 5] and [6, 7], copy 6 up. Root [6, 10, 20], which is full but legal.
  5. Insert 25 fits. Insert 28 overflows [20, 25, 28, 30]: split [20, 25] and [28, 30], copy 28 up. Now the root has 4 keys [6, 10, 20, 28] and overflows. An internal split moves the middle key 20 up: halves [6, 10] and [28], and a new root [20]. Height 3.
  6. Insert 40 fits in [28, 30, 40].

Final tree: root [20]; middle level [6, 10] and [28]; leaves [3, 5] [6, 7] [10, 12, 17] [20, 25] [28, 30, 40]. Now delete 3: the leaf [3, 5] drops to [5], below the minimum of 2. Its only sibling [6, 7] has none to spare, so the two are merged into [5, 6, 7] and the separator 6 leaves the parent.

"""A small B+ tree (insert, search, range scan) so you can see splits and measure height."""
import bisect
import random


class Node:
    def __init__(self, leaf):
        self.leaf = leaf
        self.keys = []
        self.children = []      # internal nodes only
        self.next = None        # leaf nodes only: link to the next leaf


class BPlusTree:
    def __init__(self, max_keys=3):
        self.max_keys = max_keys          # a node splits when it would hold more keys than this
        self.root = Node(leaf=True)

    # ---- search: returns (leaf, number of nodes read) ----
    def _find_leaf(self, key):
        node, reads = self.root, 1
        while not node.leaf:
            node = node.children[bisect.bisect_right(node.keys, key)]
            reads += 1
        return node, reads

    def search(self, key):
        leaf, reads = self._find_leaf(key)
        return key in leaf.keys, reads

    def range(self, lo, hi):
        leaf, reads = self._find_leaf(lo)
        out = []
        while leaf is not None:
            for k in leaf.keys:
                if k > hi:
                    return out, reads
                if k >= lo:
                    out.append(k)
            leaf = leaf.next              # follow the leaf chain: no need to climb back up
            if leaf is not None:
                reads += 1
        return out, reads

    # ---- insert ----
    def insert(self, key):
        split = self._insert(self.root, key)
        if split:                          # the root itself split: the tree grows one level
            sep, right = split
            new_root = Node(leaf=False)
            new_root.keys = [sep]
            new_root.children = [self.root, right]
            self.root = new_root

    def _insert(self, node, key):
        if node.leaf:
            i = bisect.bisect_left(node.keys, key)
            if i < len(node.keys) and node.keys[i] == key:
                return None                # duplicate key: ignore
            node.keys.insert(i, key)
            if len(node.keys) <= self.max_keys:
                return None
            mid = (len(node.keys) + 1) // 2
            right = Node(leaf=True)
            right.keys = node.keys[mid:]
            node.keys = node.keys[:mid]
            right.next, node.next = node.next, right
            return right.keys[0], right    # a leaf split COPIES the separator up
        i = bisect.bisect_right(node.keys, key)
        split = self._insert(node.children[i], key)
        if not split:
            return None
        sep, right = split
        node.keys.insert(i, sep)
        node.children.insert(i + 1, right)
        if len(node.keys) <= self.max_keys:
            return None
        mid = len(node.keys) // 2
        up = node.keys[mid]
        sibling = Node(leaf=False)
        sibling.keys = node.keys[mid + 1:]
        sibling.children = node.children[mid + 1:]
        node.keys = node.keys[:mid]
        node.children = node.children[:mid + 1]
        return up, sibling                 # an internal split MOVES the middle key up

    # ---- inspection ----
    def height(self):
        h, node = 1, self.root
        while not node.leaf:
            node, h = node.children[0], h + 1
        return h

    def levels(self):
        out, level = [], [self.root]
        while level:
            out.append(level)
            level = [c for n in level if not n.leaf for c in n.children]
        return out

    def leaf_fill(self):
        leaves = [n for n in self.levels()[-1]]
        return sum(len(n.keys) for n in leaves) / (len(leaves) * self.max_keys), len(leaves)

5. Choosing indexes for a workload

Decide which indexes a workload deserves, predict whether a query can use an index, read a query plan to confirm, and weigh read speed against write cost.

Theory

A method, not a hunch

  1. List the workload. Which queries run, and how often? Reads and writes both count. A query that runs once a year does not deserve an index; one that runs 300 times in every 1,000 operations does.
  2. Find the access paths. For each query, note the columns in WHERE (equality or range), JOIN conditions, ORDER BY or GROUP BY, and the columns it returns.
  3. Estimate selectivity. What fraction of the rows does each predicate match? A predicate that matches 0.005% of a table deserves an index. One that matches 60% does not.
  4. Design the index. Choose the columns and their order (next sections).
  5. Count the cost. Each index slows writes and takes space. Is the read gain worth it?
  6. Verify. Ask the database for the plan, run the query, and compare. Statistics can surprise you; never trust an index you did not check.

Selectivity and the break-even point

An index lookup finds a matching entry fast, but then each match may need a random block read to fetch its row. A scan reads the whole table, but in order. If the query matches a fraction f of the rows, the index costs about h + f·N reads (one per match), while a scan costs b = N / bf. They are equal near f ≈ 1 / bf, which is only a few percent. Beyond that, scanning wins.

Two situations escape this rule. If the index is clustered (the table is stored in index order), the matches sit together and the index reads only the blocks it needs. And if the index covers the query (see below), no table rows are fetched at all.

Theory

Composite indexes and the leftmost-prefix rule

A composite (multi-column) index on (a, b, c) is a B+ tree whose keys are the tuples (a, b, c), sorted by a, then b within equal a, then c within equal (a, b). Think of a phone book sorted by last name, then first name: you can find all the Smiths, or Smith + Anna, but you cannot find all the Annas without reading everything.

  • The index can be searched using a prefix of its columns: a, or (a, b), or (a, b, c). Not b alone, not (b, c).
  • Columns with equality conditions can be used one after another. The first range condition (<, >, BETWEEN, a prefix LIKE) can still be used, but it ends the seek: columns after it are only filters.
  • So list the index columns in this order: equality columns first, then the range or ORDER BY column, then any extra columns for covering.
  • An index on (a, b) also serves queries on a alone, so a separate index on (a) is usually redundant.

ORDER BY for free. Because the entries are sorted, an index can deliver rows in order without a sort step. For WHERE a = 5 ORDER BY b on an index (a, b, c), the entries for a = 5 are already in b order. With LIMIT 10, the database reads just 10 entries and stops. This is why (customer_id, created) is the right index for “a customer's 10 newest orders”.

Theory

Covering indexes

A covering index contains every column a query needs, so the answer comes from the index alone and the table is never visited. That removes the expensive random row fetches. Plans say COVERING INDEX (SQLite), Index Only Scan (PostgreSQL), or Using index (MySQL). The price is a wider, bigger index, so reserve it for hot queries. The capstone shows a covering index making one query several times faster.

Sargability: do not hide the column

A predicate is sargable (search-argument-able) when the database can use it to navigate an index. Anything that wraps or transforms the indexed column breaks that:

Theory

What an index costs

Every index is another B+ tree the DBMS must keep correct. An INSERT adds an entry to each index on the table (and may split a node); a DELETE removes one from each; an UPDATE of an indexed column moves an entry. An index also takes disk space and cache. def best_ms(sql, params=(), repeat=5):
    """Best of several runs, in milliseconds (best-of reduces noise from other programs)."""
    best = None
    for _ in range(repeat):
        t0 = time.perf_counter()
        conn.execute(sql, params).fetchall()
        dt = (time.perf_counter() - t0) * 1000
        best = dt if best is None or dt < best else best
    return best

def plan(sql, params):
    return " | ".join(r[3] for r in conn.execute("EXPLAIN QUERY PLAN " + sql, params))


def avg_ms(sql, make_params, runs):
    t0 = time.perf_counter()
    for _ in range(runs):
        conn.execute(sql, make_params()).fetchall()
    return (time.perf_counter() - t0) * 1000 / runs

    ms = avg_ms(sql, mk, runs)

    print(f"{name:<36}{ms:>9.3f}   {plan(sql, mk())}")

Reading the result. W1, W2, and W3 drop from milliseconds to a few hundredths of a millisecond: each is a single seek. W4 improves a lot, but W5 improves much less, because it still matches about 9% of the table and needs a row lookup for every match. Notice that inserts get slower, because each insert now maintains four more B+ trees.

Extension. Change the last index to (status, created, total). Now W4 and W5 are answered from the index alone (COVERING INDEX), and W5 gets several times faster than with the narrower index. Is it worth the extra width? That depends on how often W5 runs, which is the whole point.
