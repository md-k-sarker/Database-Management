01Start here

SQL is the language you use to talk to a relational database. This module teaches the five groups of statements you will use for the rest of the course: defining tables, changing data, asking questions, combining tables, and keeping the data correct.

How this tutorial works

  • Every code block can be copied. Paste it into MySQL Workbench and run it yourself. Type the examples at least once; your fingers learn syntax faster than your eyes.
  • Every Output box was produced by a real MySQL 8.4 server, not typed by hand. Row order without ORDER BY can differ on your machine, so do not worry if it does.
  • Near the end there is an in-browser practice lab with auto-checked challenges. It runs SQLite inside your browser, so you can practice without installing anything. The page tells you where SQLite and MySQL differ.
Before you start

You need a working MySQL server and Workbench from Module 0. In Workbench, open a connection to your local server before you continue.

02Defining tables (DDL)

DDL statements define the structure of the database: its tables, columns, data types and rules. The rules (constraints) are what keep bad data out, so they are the most important part.

CREATE TABLE with constraints

We will build a tiny club-membership design in a separate practice database called dbm_demo, so your university data stays untouched. Read the comments: each constraint is one rule the database will enforce for you.

SQL
CREATE DATABASE dbm_demo;
USE dbm_demo;

CREATE TABLE club (
  club_id  INT AUTO_INCREMENT PRIMARY KEY,   -- unique, never NULL, numbered automatically
  name     VARCHAR(50) NOT NULL UNIQUE,      -- required, and no two clubs share a name
  founded  INT CHECK (founded >= 1800)       -- a rule about the value itself
);

CREATE TABLE member (
  member_id INT AUTO_INCREMENT PRIMARY KEY,
  club_id   INT NOT NULL,
  email     VARCHAR(80) NOT NULL UNIQUE,
  joined    DATE NOT NULL DEFAULT (CURRENT_DATE),   -- used when you do not supply a value
  FOREIGN KEY (club_id) REFERENCES club(club_id)    -- every member must belong to a real club
);
Output (MySQL 8.4)
Query OK, 1 row affected

Query OK, 0 rows affected

Query OK, 0 rows affected

Output (MySQL 8.4)

Reading errors

Read an error message from left to right: the number (1062), the SQLSTATE code in brackets, then the explanation. The explanation almost always names the table, the column or the constraint that was violated. Google the number if the words do not help.

What happens to the children? ON DELETE and ON UPDATE

By default a foreign key blocks the deletion of a parent row that still has children (the last error above). You can choose a different behaviour when you declare the key:

OptionMeaning when the parent row is deleted
RESTRICT or NO ACTION (default)Refuse the delete.
CASCADEDelete the child rows too.
SET NULLKeep the child rows but set the foreign key column to NULL (the column must allow NULL).
SQL
USE dbm_demo;
CREATE TABLE post (
  post_id INT AUTO_INCREMENT PRIMARY KEY,
  club_id INT NOT NULL,
  body    VARCHAR(100) NOT NULL,
  FOREIGN KEY (club_id) REFERENCES club(club_id) ON DELETE CASCADE
);
INSERT INTO post (club_id, body) VALUES (2, 'First meeting Friday'), (2, 'Bring a laptop');
SELECT * FROM post;
DELETE FROM club WHERE club_id = 2;
SELECT * FROM post;
Output (MySQL 8.4)
+---------+---------+----------------------+
| post_id | club_id | body                 |
+---------+---------+----------------------+
|       1 |       2 | First meeting Friday |
|       2 |       2 | Bring a laptop       |
+---------+---------+----------------------+
2 rows in set

Empty set

Deleting the Robotics club removed its posts automatically. CASCADE is powerful and therefore dangerous: use it only when the children truly have no meaning without the parent.

ALTER TABLE and DROP TABLE

ALTER TABLE changes a table that already exists, and it can do it even when the table holds data.

SQL
USE dbm_demo;
ALTER TABLE club ADD COLUMN website VARCHAR(100);                  -- new column, NULL for existing rows
ALTER TABLE club MODIFY COLUMN website VARCHAR(200);               -- change its type
ALTER TABLE club RENAME COLUMN website TO url;                     -- rename
ALTER TABLE club ADD CONSTRAINT uq_club_url UNIQUE (url);          -- add a rule later
ALTER TABLE club DROP COLUMN url;                                  -- remove (the unique rule goes with it)
DESCRIBE club;
Output (MySQL 8.4)
+---------+-------------+------+-----+---------+----------------+
| Field   | Type        | Null | Key | Default | Extra          |
+---------+-------------+------+-----+---------+----------------+
| club_id | int         | NO   | PRI | NULL    | auto_increment |
| name    | varchar(50) | NO   | UNI | NULL    |                |
| founded | int         | YES  |     | NULL    |                |
+---------+-------------+------+-----+---------+----------------+
3 rows in set

To remove a table, use DROP TABLE. Order matters when tables are linked: MySQL refuses to drop a parent while a child still points at it.

SQL
USE dbm_demo;
DROP TABLE club;                    -- member and post still reference it
DROP TABLE post, member, club;      -- children first (listing them together also works)
SHOW TABLES;
Output (MySQL 8.4)
ERROR 3730 (HY000): Cannot drop table 'club' referenced by a foreign key constraint 'member_ibfk_1' on table 'member'.

Empty set
Watch out

DROP TABLE and TRUNCATE TABLE cannot be undone, and in MySQL they end any open transaction. There is no recycle bin. Always check which database you are in (SELECT DATABASE();) before running them.

03Changing data (DML)

DML statements change the data inside tables that already exist: INSERT adds rows, UPDATE changes them, DELETE removes them. They are short to write and easy to get wrong, so this section is about doing them safely.

Work on a copy

To protect your university data, we first make a throwaway copy of the student table and practise on the copy. This is a good habit on real systems too. CREATE TABLE ... LIKE copies the columns and indexes (not the foreign keys), and INSERT ... SELECT copies the rows.

SQL
CREATE TABLE student_copy LIKE student;
INSERT INTO student_copy SELECT * FROM student;
SELECT COUNT(*) AS copied FROM student_copy;
Output (MySQL 8.4)
Query OK, 0 rows affected

Query OK, 12 rows affected
Records: 12  Duplicates: 0  Warnings: 0

+--------+
| copied |
+--------+
|     12 |
+--------+
1 row in set

INSERT

Always list the columns you are filling. It keeps working when someone adds a column later, and it makes the statement readable. Columns you leave out get their default value, which is NULL unless you declared another.

SQL
INSERT INTO student_copy (sid, name, major, gpa)
VALUES (13, 'Maya Singh', 'Physics', 3.45);

-- several rows in one statement
INSERT INTO student_copy (sid, name, major, gpa) VALUES
  (14, 'Noah Fischer',  'History', 3.25),
  (15, 'Olivia Grant',  'Physics', 3.80);

SELECT sid, name, phone FROM student_copy WHERE sid >= 13;
Output (MySQL 8.4)
Query OK, 1 row affected

Query OK, 0 rows affected

Query OK, 2 rows affected
Records: 2  Duplicates: 0  Warnings: 0

| sid | name         | phone |
+-----+--------------+-------+
|  13 | Maya Singh   | NULL  |
|  14 | Noah Fischer | NULL  |
|  15 | Olivia Grant | NULL  |
+-----+--------------+-------+

The first two statements report how many rows they touched; the phone column is NULL because we never supplied it. Now two ways to fail:

SQL
INSERT INTO student_copy (sid, name) VALUES (13, 'Duplicate Id');      -- sid 13 already exists
INSERT INTO student_copy (sid, name) VALUES (16);                       -- 2 columns, 1 value

mysql> INSERT INTO student_copy (sid, name) VALUES (13, 'Duplicate Id')

mysql> INSERT INTO student_copy (sid, name) VALUES (16)
ERROR 1136 (21S01): Column count doesn't match value count at row 1

UPDATE

UPDATE sets new values on the rows chosen by WHERE. Without a WHERE, it changes every row.

SQL
UPDATE student_copy SET phone = '555-0113' WHERE sid = 13;
UPDATE student_copy SET major = 'Data Science', gpa = gpa + 0.05 WHERE sid IN (14, 15);
SELECT sid, name, major, gpa, phone FROM student_copy WHERE sid >= 13;
Output (MySQL 8.4)
Query OK, 1 row affected
Rows matched: 1  Changed: 1  Warnings: 0

Query OK, 2 rows affected
Rows matched: 2  Changed: 2  Warnings: 0

+-----+--------------+--------------+------+----------+
| sid | name         | major        | gpa  | phone    |
+-----+--------------+--------------+------+----------+
|  13 | Maya Singh   | Physics      | 3.45 | 555-0113 |
|  14 | Noah Fischer | Data Science | 3.30 | NULL     |
|  15 | Olivia Grant | Data Science | 3.85 | NULL     |
+-----+--------------+--------------+------+----------+
3 rows in set

The second statement matched two rows and changed two. The line Rows matched: 2 Changed: 2 is your proof that it touched exactly what you expected. Always read it.

Common mistake

Forgetting the WHERE is the classic disaster: UPDATE student_copy SET gpa = 0.00; zeroes every student. MySQL Workbench has a Safe Updates option (Edit, Preferences, SQL Editor) that refuses an UPDATE or DELETE that has no key in its WHERE. The command-line client has the same protection with --safe-updates. This is the message you get:

Output (MySQL 8.4, safe updates on)
ERROR 1175 (HY000): You are using safe update mode and you tried to update a table without a WHERE that uses a KEY column.

A good routine: first run SELECT ... WHERE ... to see which rows you are about to change, and only then turn the SELECT into an UPDATE or DELETE.

DELETE and TRUNCATE

SQL
DELETE FROM student_copy WHERE sid = 15;
DELETE FROM student_copy WHERE gpa IS NULL;
SELECT COUNT(*) AS remaining FROM student_copy;
Output (MySQL 8.4)
Query OK, 1 row affected

Query OK, 1 row affected

+-----------+
| remaining |
+-----------+
|        13 |
+-----------+
1 row in set

DELETE removes the rows you select, one by one, and can be undone inside a transaction (section 8). TRUNCATE TABLE empties the whole table at once. It is faster, it resets AUTO_INCREMENT counters, and it is a DDL statement, so it commits immediately and cannot be rolled back. MySQL also refuses to truncate a table that another table's foreign key points at.

SQL
TRUNCATE TABLE student;                -- student is referenced by enrollment
TRUNCATE TABLE student_copy;           -- the copy has no foreign keys
SELECT COUNT(*) AS in_copy FROM student_copy;
DROP TABLE student_copy;
Output (MySQL 8.4)
mysql> TRUNCATE TABLE student
ERROR 1701 (42000): Cannot truncate a table referenced in a foreign key constraint (`university`.`enrollment`, CONSTRAINT `enrollment_ibfk_1`)

mysql> SELECT COUNT(*) AS in_copy FROM student_copy
+---------+
| in_copy |
+---------+
|       0 |
+---------+
1 row in set

Upsert: insert or update in one statement

MySQL's INSERT ... ON DUPLICATE KEY UPDATE inserts a row, or, if the primary key (or a unique key) already exists, updates the existing row instead. PostgreSQL and SQLite spell this ON CONFLICT, as Module 5 shows.

SQL
USE dbm_demo;
CREATE TABLE visit_count (page VARCHAR(30) PRIMARY KEY, hits INT NOT NULL);
INSERT INTO visit_count VALUES ('home', 1) ON DUPLICATE KEY UPDATE hits = hits + 1;
INSERT INTO visit_count VALUES ('home', 1) ON DUPLICATE KEY UPDATE hits = hits + 1;
INSERT INTO visit_count VALUES ('about', 1) ON DUPLICATE KEY UPDATE hits = hits + 1;
SELECT * FROM visit_count ORDER BY page;
DROP TABLE visit_count;
Output (MySQL 8.4)
+-------+------+
| page  | hits |
+-------+------+
| about |    1 |
| home  |    2 |
+-------+------+
2 rows in set

04Asking questions (SELECT)

SELECT is how you ask questions. Its power comes from a handful of clauses that you combine like Lego: choose columns, filter rows, sort, and limit.

The anatomy of a query

SQL
SELECT   column_list            -- 5. which columns (and expressions) to show
FROM     table_name             -- 1. which table to read
WHERE    row_condition          -- 2. keep only rows that satisfy this
GROUP BY grouping_columns       -- 3. (section 6) form groups
HAVING   group_condition        -- 4. (section 6) keep only some groups
ORDER BY sort_columns           -- 6. sort the result
LIMIT    row_count;             -- 7. keep only the first rows

The numbers show the order in which the database logically works, which is not the order you write the clauses. That explains a classic error: a column alias created in SELECT (step 5) does not exist yet when WHERE (step 2) runs.

SQL
SELECT name, gpa * 10 AS score FROM student WHERE score > 35;
Output (MySQL 8.4)
mysql> SELECT name, gpa * 10 AS score FROM student WHERE score > 35
ERROR 1054 (42S22): Unknown column 'score' in 'where clause'

SELECT name, major FROM student;                                 -- two columns

Combining conditions: AND binds tighter than OR

This is a frequent source of wrong answers. AND is evaluated before OR, exactly like multiplication before addition. When in doubt, add parentheses.

SQL
-- reads as: Mathematics  OR  (Physics AND gpa > 3.2)
SELECT name, major, gpa FROM student
WHERE major = 'Mathematics' OR major = 'Physics' AND gpa > 3.2;

-- what you probably meant: (Mathematics OR Physics) AND gpa > 3.2
SELECT name, major, gpa FROM student
WHERE (major = 'Mathematics' OR major = 'Physics') AND gpa > 3.2;

Pattern matching with LIKE

% matches any number of characters (including none) and _ matches exactly one. In MySQL's default collation, LIKE ignores upper and lower case (and accents), unlike PostgreSQL, where LIKE is case-sensitive.

SQL
SELECT name FROM student WHERE name LIKE 'c%';       -- starts with c or C
SELECT name FROM student WHERE name LIKE '%son';     -- ends with son
SELECT name FROM student WHERE name LIKE '_a%';      -- second letter is a

NULL: the value that is not a value

NULL means "unknown" or "not applicable". Because the truth of a comparison with an unknown is itself unknown, SQL uses three-valued logic: TRUE, FALSE and UNKNOWN. A WHERE clause keeps a row only if the condition is TRUE; rows where it is FALSE or UNKNOWN are dropped.

SQL
SELECT name, gpa FROM student WHERE gpa = NULL;        -- never true, not even for NULL rows
SELECT name, gpa FROM student WHERE gpa IS NULL;       -- the correct test
SELECT name, phone FROM student WHERE phone IS NOT NULL AND sid <= 5;

Empty set

05Combining tables (joins)

Good database design splits data across tables, so almost every useful question needs a join: combine rows from two tables whose key values match. The join type decides what happens to the rows that have no match.

INNER JOIN: only the matches

Which course titles has each student taken? Student names live in student, course titles in course, and enrollment is the bridge between them.

SQL
SELECT s.name, c.title, e.term
FROM student AS s
JOIN enrollment AS e ON e.sid = s.sid
JOIN course AS c     ON c.course_id = e.course_id
WHERE s.sid IN (1, 4)
ORDER BY s.name, c.title;
Output (MySQL 8.4)
+--------------+-----------------------+-----------+
| name         | title                 | term      |
+--------------+-----------------------+-----------+
| Ada Lovelace | Calculus I            | Fall 2025 |
| Ada Lovelace | Data Structures       | Fall 2026 |
| Ada Lovelace | Intro to Programming  | Fall 2025 |
| Dev Patel    | Calculus I            | Fall 2025 |
| Dev Patel    | Intro to Data Science | Fall 2025 |
| Dev Patel    | Intro to Programming  | Fall 2025 |
+--------------+-----------------------+-----------+
6 rows in set

Read it as: start with student, attach each matching enrollment row, attach each matching course row, and then filter. s, e and c are table aliases; they save typing and are required when you join a table to itself. The rule that matches rows is the ON condition, almost always foreign_key = primary_key.

When both columns have the same name you can write JOIN enrollment USING (sid), which also merges the two sid columns into one in SELECT *.

Why the join type matters

Students 9 and 12 have no enrollments. An inner join silently drops them. That is correct when you only care about enrolled students, and a bug when you wanted "all students and their course counts".

The explorer above uses two tiny tables (their rows are shown). Experiment with every join type and watch which rows get a NULL partner. Next, the same idea on the real data.

LEFT JOIN: keep everything from the left table

SELECT s.sid, s.name, e.course_id

WHERE s.sid IN (8, 9, 12)
ORDER BY s.sid, e.course_id;
Output (MySQL 8.4)

|   9 | Imani Brown    | NULL      |
|  12 | Liam O'Connor  | NULL      |

4 rows in set

Students 9 and 12 appear with NULL where the enrollment columns would be. This gives a very useful pattern, the anti-join: "find the rows that have no match" means left join, then keep the rows where the right side is NULL.

SELECT s.sid, s.name

Filter in WHERE or in ON?

Where you put a condition on the right-hand table matters in a LEFT JOIN. A condition in WHERE runs after the join and can silently turn it back into an inner join; a condition in ON only decides what counts as a match. Compare:

SQL
SELECT s.name, e.course_id FROM student s
LEFT JOIN enrollment e ON e.sid = s.sid
WHERE e.term = 'Fall 2026' AND s.sid IN (1, 9);      -- student 9 vanishes

SELECT s.name, e.course_id FROM student s
LEFT JOIN enrollment e ON e.sid = s.sid AND e.term = 'Fall 2026'
WHERE s.sid IN (1, 9);                                 -- student 9 stays, with NULL
Output (MySQL 8.4)

| name         | course_id |

1 row in set

+--------------+-----------+
| Ada Lovelace | CS201     |
| Imani Brown  | NULL      |
+--------------+-----------+
2 rows in set

RIGHT JOIN and FULL OUTER JOIN

RIGHT JOIN is simply LEFT JOIN with the tables swapped; most people always write LEFT for readability. A full outer join (keep unmatched rows from both sides) exists in standard SQL but MySQL does not have it. You emulate it by uniting a left and a right join. The two tiny tables below are the ones from the explorer: jl has ids 1 to 4, jr has ids 2, 3, 3 and 5.

SQL
SELECT jl.id, jl.name, jr.id AS r_id, jr.course
FROM jl LEFT JOIN jr ON jl.id = jr.id
UNION
SELECT jl.id, jl.name, jr.id, jr.course
FROM jl RIGHT JOIN jr ON jl.id = jr.id
ORDER BY id, r_id, course;
Output (MySQL 8.4)
+------+-------+------+---------+
| id   | name  | r_id | course  |
+------+-------+------+---------+
| NULL | NULL  |    5 | PHYS101 |
|    1 | Ada   | NULL | NULL    |
|    2 | Ben   |    2 | MATH101 |
|    3 | Carla |    3 | CS101   |
|    3 | Carla |    3 | CS201   |
|    4 | Dev   | NULL | NULL    |
+------+-------+------+---------+
6 rows in set

UNION removes duplicate rows between the two halves; the inner-join rows appear in both, so without it they would be repeated. (UNION ALL keeps duplicates.)

CROSS JOIN and the missing ON clause

A cross join pairs every row of one table with every row of the other. With 12 students and 10 courses that is 120 rows. This is rarely what you want, and it is exactly what you get if you list two tables and forget the join condition.

SQL
SELECT COUNT(*) AS rows_from_cross_join FROM student CROSS JOIN course;
SELECT COUNT(*) AS forgot_the_on_clause FROM student, course;      -- the old comma syntax
Output (MySQL 8.4)
+----------------------+
| rows_from_cross_join |
+----------------------+
|                  120 |
+----------------------+
1 row in set

+----------------------+
| forgot_the_on_clause |
+----------------------+
|                  120 |
+----------------------+
1 row in set

If a query suddenly returns far too many rows, check that every table in the FROM clause is connected by an ON condition.

Self join: a table joined to itself

Which pairs of students share a major? Treat the same table as two copies with different aliases. s1.sid < s2.sid keeps each pair once and removes pairing a student with themselves.

SELECT s1.name AS student_1, s2.name AS student_2, s1.major
FROM student s1
JOIN student s2 ON s1.major = s2.major AND s1.sid < s2.sid
WHERE s1.major = 'Mathematics'
ORDER BY s1.sid, s2.sid;
Output (MySQL 8.4)

06Summarizing data (GROUP BY)

Aggregate functions collapse many rows into one answer: how many, how much, what average. GROUP BY does that once per group instead of once for the whole table.

The five aggregates

SQL
SELECT COUNT(*)             AS all_rows,
       COUNT(gpa)           AS rows_with_gpa,
       COUNT(DISTINCT major) AS distinct_majors,
       MIN(gpa)             AS lowest,
       MAX(gpa)             AS highest,
       ROUND(AVG(gpa), 3)   AS average,
       SUM(gpa)             AS total
FROM student;
Output (MySQL 8.4)
+----------+---------------+-----------------+--------+---------+---------+-------+
| all_rows | rows_with_gpa | distinct_majors | lowest | highest | average | total |
+----------+---------------+-----------------+--------+---------+---------+-------+
|       12 |            11 |               4 |   2.90 |    3.90 |   3.450 | 37.95 |
+----------+---------------+-----------------+--------+---------+---------+-------+
1 row in set

Three things to remember:

  • COUNT(*) counts rows. COUNT(column) counts rows where that column is not NULL. That is why the table above shows 12 rows but only 11 GPAs.
  • Every aggregate except COUNT(*) ignores NULLs. The average is over 11 students, not 12. If you want NULL treated as zero, say so with AVG(COALESCE(gpa, 0)), and think about whether that is honest.
  • COUNT(DISTINCT col) counts different values: four majors, because NULL is not counted.

GROUP BY

Add GROUP BY and the aggregates are computed separately for each value of the grouping column.

SQL
SELECT major,
       COUNT(*)           AS students,
       ROUND(AVG(gpa), 2) AS avg_gpa,
       MAX(gpa)           AS best
FROM student
GROUP BY major
ORDER BY students DESC, major;
Output (MySQL 8.4)
+------------------+----------+---------+------+
| major            | students | avg_gpa | best |
+------------------+----------+---------+------+
| Computer Science |        4 |    3.72 | 3.90 |
| Data Science     |        3 |    3.55 | 3.85 |
| Mathematics      |        3 |    3.35 | 3.75 |
| NULL             |        1 |    3.00 | 3.00 |
| Physics          |        1 |    3.10 | 3.10 |
+------------------+----------+---------+------+
5 rows in set

Students with major IS NULL form a group of their own (the row with NULL above). Computer Science has 4 students but an average over only 3 GPAs, since Imani has none yet.

Step through it below to see how the groups are formed before the aggregates are computed.

WHERE filters rows, HAVING filters groups

WHERE runs before grouping, so it cannot see an aggregate. HAVING runs after grouping and can. Use WHERE for conditions on individual rows and HAVING for conditions on aggregates; putting row conditions in WHERE is also faster, because fewer rows reach the grouping step.

SQL
SELECT major, COUNT(*) AS students, ROUND(AVG(gpa), 2) AS avg_gpa
FROM student
WHERE gpa IS NOT NULL            -- row filter, before grouping
GROUP BY major
HAVING COUNT(*) >= 3             -- group filter, after grouping
ORDER BY avg_gpa DESC;
Output (MySQL 8.4)
+------------------+----------+---------+
| major            | students | avg_gpa |
+------------------+----------+---------+
| Computer Science |        3 |    3.72 |
| Data Science     |        3 |    3.55 |
| Mathematics      |        3 |    3.35 |
+------------------+----------+---------+
3 rows in set
SQL
SELECT major, AVG(gpa) FROM student WHERE AVG(gpa) > 3.5 GROUP BY major;
Output (MySQL 8.4)
mysql> SELECT major, AVG(gpa) FROM student WHERE AVG(gpa) > 3.5 GROUP BY major
ERROR 1111 (HY000): Invalid use of group function

The ONLY_FULL_GROUP_BY rule

Every column in SELECT must either be in the GROUP BY list or be inside an aggregate. Otherwise the database would have to guess which of the group's values to show. MySQL's default sql_mode enforces this:

SQL
SELECT major, name, COUNT(*) FROM student GROUP BY major;
Output (MySQL 8.4)
mysql> SELECT major, name, COUNT(*) FROM student GROUP BY major
ERROR 1055 (42000): Expression #2 of SELECT list is not in GROUP BY clause and contains nonaggregated column 'university.student.name' which is not functionally dependent on columns in GROUP BY clause; this is incompatible with sql_mode=only_full_group_by

Fix it by deciding what you really want: add name to the GROUP BY (one group per student, probably not intended), drop it, or aggregate it (MAX(name), GROUP_CONCAT(name)).

SQL
SELECT major, COUNT(*) AS students, GROUP_CONCAT(name ORDER BY name SEPARATOR ', ') AS who
FROM student
WHERE major IS NOT NULL
GROUP BY major
ORDER BY major;
Output (MySQL 8.4)
+------------------+----------+-----------------------------------------------------+
| major            | students | who                                                 |
+------------------+----------+-----------------------------------------------------+
| Computer Science |        4 | Ada Lovelace, Carla Diaz, Emma Johnson, Imani Brown |
| Data Science     |        3 | Dev Patel, Grace Kim, Jun Park                      |
| Mathematics      |        3 | Ben Carter, Farid Rahman, Kayla Nguyen              |
| Physics          |        1 | Hector Alvarez                                      |
+------------------+----------+-----------------------------------------------------+
4 rows in set

Grouping over a join, and the COUNT(*) trap

How many students are enrolled in each course, including courses nobody takes? That needs a left join from course. Watch the difference between COUNT(*) and COUNT(e.sid):

SQL
SELECT c.course_id, c.title,
       COUNT(*)     AS count_star,      -- counts the row, even the NULL-padded one
       COUNT(e.sid) AS enrolled         -- counts only real enrollments
FROM course c
LEFT JOIN enrollment e ON e.course_id = c.course_id
GROUP BY c.course_id, c.title
ORDER BY enrolled DESC, c.course_id;
Output (MySQL 8.4)
+-----------+-----------------------+------------+----------+
| course_id | title                 | count_star | enrolled |
+-----------+-----------------------+------------+----------+
| CS101     | Intro to Programming  |          7 |        7 |
| MATH101   | Calculus I            |          6 |        6 |
| CS201     | Data Structures       |          3 |        3 |
| DS110     | Intro to Data Science |          3 |        3 |
| MATH201   | Linear Algebra        |          3 |        3 |
| DS210     | Machine Learning      |          2 |        2 |
| PHYS101   | Physics I             |          2 |        2 |
| CS301     | Database Management   |          1 |        1 |
| HIST101   | World History         |          1 |        1 |
| CS450     | Special Topics        |          1 |        0 |

CS450 has nobody enrolled, yet COUNT(*) reports 1, because the left join produced one row with NULL in the enrollment columns. COUNT(e.sid) correctly says 0. Whenever you count over an outer join, count a column from the optional side.

5 rows in set

The last row, with NULL instead of a major, is the grand total (11 students who have a declared major).

07Subqueries and CTEs

A subquery is a query inside another query. It lets you answer a question in steps: first find something, then use it. This section also introduces common table expressions (CTEs), set operators and window functions, all available in MySQL 8.4.

Scalar subquery: one value

Who has a GPA above the university average? The inner query returns a single number that the outer query compares against.

SELECT name, gpa FROM student
WHERE gpa > (SELECT AVG(gpa) FROM student)
ORDER BY gpa DESC;

IN and EXISTS: a list, or a yes/no

Who is enrolled in a Computer Science course? Two equivalent formulations:

              WHERE c.dept_name = 'Computer Science')
ORDER BY name;

SELECT s.name FROM student s
WHERE EXISTS (SELECT 1 FROM enrollment e JOIN course c ON c.course_id = e.course_id
              WHERE e.sid = s.sid AND c.dept_name = 'Computer Science')
ORDER BY s.name;

The NOT IN trap

Find the instructors who do not teach a Computer Science course. The natural query returns nothing, which is wrong:

SQL
SELECT name FROM instructor
WHERE iid NOT IN (SELECT iid FROM course WHERE dept_name = 'Computer Science');
Output (MySQL 8.4)
Empty set

Why? Course CS450 has iid = NULL, so the list contains a NULL. For any instructor, iid NOT IN (1, 2, NULL) means iid <> 1 AND iid <> 2 AND iid <> NULL, and the last comparison is UNKNOWN, so the whole condition is never true. Two safe fixes:

SQL
-- fix 1: remove the NULLs from the list
SELECT name FROM instructor
WHERE iid NOT IN (SELECT iid FROM course WHERE dept_name = 'Computer Science' AND iid IS NOT NULL);

-- fix 2: NOT EXISTS ignores NULLs naturally
SELECT i.name FROM instructor i
WHERE NOT EXISTS (SELECT 1 FROM course c WHERE c.iid = i.iid AND c.dept_name = 'Computer Science');
Output (MySQL 8.4)
+---------------+
| name          |
+---------------+
| Mei Tanaka    |
| Samuel Brooks |
| Hana Petrov   |
| Jonah Reyes   |

4 rows in set

+---------------+
| name          |
+---------------+
| Mei Tanaka    |
| Samuel Brooks |
| Hana Petrov   |
| Jonah Reyes   |
+---------------+
4 rows in set
Watch out

08Transactions and views

Two tools keep data trustworthy as it changes: transactions make a group of changes succeed or fail as one unit, and views give users a safe, simplified window onto the tables.

Transactions: all or nothing

Moving money between two accounts takes two updates. If the program stops after the first, money vanishes. A transaction groups the statements so that either all of them take effect (COMMIT) or none do (ROLLBACK). Here is a small bank in the practice database:

SQL
USE dbm_demo;
CREATE TABLE account (
  acct_id INT PRIMARY KEY,
  owner   VARCHAR(30) NOT NULL,
  balance DECIMAL(8,2) NOT NULL CHECK (balance >= 0)
) ENGINE=InnoDB;
INSERT INTO account VALUES (1, 'Ada', 500.00), (2, 'Ben', 100.00);
SELECT @@autocommit;
Output (MySQL 8.4)
+--------------+
| @@autocommit |
+--------------+
|            1 |
+--------------+
1 row in set

By default MySQL runs in autocommit mode (@@autocommit = 1): every statement is its own tiny transaction and is saved immediately. START TRANSACTION switches that off until you COMMIT or ROLLBACK. Tables must use the InnoDB storage engine for this; it is the default in MySQL 8.4.

SQL
USE dbm_demo;
START TRANSACTION;
UPDATE account SET balance = balance - 200 WHERE acct_id = 1;
UPDATE account SET balance = balance + 200 WHERE acct_id = 2;
SELECT * FROM account;      -- we can see our own changes...
COMMIT;                     -- ...and now everyone can
Output (MySQL 8.4)
+---------+-------+---------+
| acct_id | owner | balance |
+---------+-------+---------+
|       1 | Ada   |  300.00 |
|       2 | Ben   |  300.00 |
+---------+-------+---------+
2 rows in set

When something goes wrong

Now a transfer that cannot work: Ada only has 300 left. We credit Ben first, and then the debit violates the CHECK (balance >= 0) rule.

SQL
USE dbm_demo;
START TRANSACTION;
UPDATE account SET balance = balance + 900 WHERE acct_id = 2;
UPDATE account SET balance = balance - 900 WHERE acct_id = 1;     -- fails
SELECT * FROM account;      -- Ben already shows the extra 900!
ROLLBACK;
SELECT * FROM account;      -- everything is back
Output (MySQL 8.4)
mysql> UPDATE account SET balance = balance - 900 WHERE acct_id = 1
ERROR 3819 (HY000): Check constraint 'account_chk_1' is violated.

mysql> SELECT * FROM account
+---------+-------+---------+
| acct_id | owner | balance |
+---------+-------+---------+
|       1 | Ada   |  300.00 |
|       2 | Ben   | 1200.00 |
+---------+-------+---------+
2 rows in set

mysql> SELECT * FROM account
+---------+-------+---------+

Notice something subtle: the failed statement undid only itself. The first update was still pending inside the transaction, so Ben showed 1200 until we issued ROLLBACK. In real code, your program must catch the error and decide to roll back. Rolling back also rescues you from your own mistakes:

SQL
USE dbm_demo;
START TRANSACTION;
DELETE FROM account;                       -- oops, no WHERE
SELECT COUNT(*) AS rows_left FROM account;
ROLLBACK;
SELECT COUNT(*) AS rows_left FROM account;
Output (MySQL 8.4)
+-----------+
| rows_left |
+-----------+
|         0 |
+-----------+
1 row in set

+-----------+
| rows_left |
+-----------+
|         2 |
+-----------+
1 row in set

Savepoints

A SAVEPOINT marks a spot inside a transaction that you can roll back to without discarding everything before it.

SQL
USE dbm_demo;
START TRANSACTION;
INSERT INTO account VALUES (3, 'Cy', 50);
SAVEPOINT after_cy;
INSERT INTO account VALUES (4, 'Di', 75);
ROLLBACK TO SAVEPOINT after_cy;            -- undo only Di
SELECT * FROM account ORDER BY acct_id;
ROLLBACK;                                  -- undo the rest
Output (MySQL 8.4)
+---------+-------+---------+
| acct_id | owner | balance |
+---------+-------+---------+
|       1 | Ada   |  300.00 |
|       2 | Ben   |  300.00 |
|       3 | Cy    |   50.00 |
+---------+-------+---------+
3 rows in set
DDL commits

In MySQL, DDL statements such as CREATE TABLE, ALTER TABLE and DROP TABLE cause an implicit commit: they silently end your transaction and make everything so far permanent. Watch the insert survive the ROLLBACK below:

SQL
USE dbm_demo;
START TRANSACTION;
INSERT INTO account VALUES (5, 'Eve', 10);
CREATE TABLE scratch (x INT);              -- implicit COMMIT happens here
ROLLBACK;                                  -- too late: nothing left to roll back
SELECT * FROM account ORDER BY acct_id;
DROP TABLE scratch;
Output (MySQL 8.4)
+---------+-------+---------+
| acct_id | owner | balance |
+---------+-------+---------+
|       1 | Ada   |  300.00 |
|       2 | Ben   |  300.00 |
|       5 | Eve   |   10.00 |
+---------+-------+---------+
3 rows in set

These guarantees have a name, ACID (atomicity, consistency, isolation, durability), and Module 10 studies them properly, including what happens when two users run transactions at the same time.

Views: a saved query with a name

A view stores a query, not data. Selecting from it runs the stored query against the base tables, so it is always current. Views simplify repeated joins and let you expose only some columns to certain users.

SQL
CREATE VIEW cs_students AS
  SELECT sid, name, gpa FROM student WHERE major = 'Computer Science';

SELECT * FROM cs_students ORDER BY sid;
Output (MySQL 8.4)
+-----+--------------+------+
| sid | name         | gpa  |
+-----+--------------+------+
|   1 | Ada Lovelace | 3.90 |
|   3 | Carla Diaz   | 3.70 |
|   5 | Emma Johnson | 3.55 |
|   9 | Imani Brown  | NULL |
+-----+--------------+------+
4 rows in set

Simple views like this one are updatable: changing a row through the view changes the base table. Try it inside a transaction so we can undo it:

SQL
START TRANSACTION;
UPDATE cs_students SET gpa = 3.95 WHERE sid = 1;
SELECT sid, name, gpa FROM student WHERE sid = 1;       -- the base table changed
ROLLBACK;
SELECT sid, name, gpa FROM student WHERE sid = 1;
Output (MySQL 8.4)
+-----+--------------+------+
| sid | name         | gpa  |
+-----+--------------+------+
|   1 | Ada Lovelace | 3.95 |
+-----+--------------+------+
1 row in set

+-----+--------------+------+
| sid | name         | gpa  |
+-----+--------------+------+
|   1 | Ada Lovelace | 3.90 |
+-----+--------------+------+
1 row in set

One danger: through a view you can insert a row that the view itself would not show. WITH CHECK OPTION forbids that:

SQL
CREATE VIEW cs_students_checked AS
  SELECT sid, name, major, gpa FROM student WHERE major = 'Computer Science'
  WITH CHECK OPTION;

INSERT INTO cs_students_checked (sid, name, major, gpa) VALUES (20, 'Pat Lee', 'History', 3.0);

DROP VIEW cs_students, cs_students_checked;
Output (MySQL 8.4)
ERROR 1369 (HY000): CHECK OPTION failed 'university.cs_students_checked'

Views that use GROUP BY, DISTINCT, aggregates or UNION are read-only. Views are also a basic security tool: you can GRANT a user access to a view without giving access to the underlying table (Module 10).

A debugging routine that works

  1. Read the whole message, then the number, then the words after near.
  2. Shrink the problem. Comment out joins and conditions until it runs, then add them back one at a time.
  3. Look at intermediate results. Run each subquery or CTE on its own. Replace SELECT columns with COUNT(*) to see if a join multiplies rows.
  4. Check your assumptions about the data (NULLs, duplicates, spaces, upper and lower case).
  5. Sanity-check totals. Does the row count make sense? Do the groups add up to the whole?

EXPLAIN: how MySQL will run your query

Writing a query that returns the right rows comes first. Making it fast comes second, and the main tool is EXPLAIN, which shows the plan without running the query. The most important column is type, how MySQL reaches the rows: const and ref use an index to jump straight to matching rows, ALL reads the entire table.

SQL
EXPLAIN SELECT * FROM student WHERE sid = 3;
EXPLAIN SELECT * FROM student WHERE name = 'Ada Lovelace';
Output (MySQL 8.4)
+----+-------------+---------+------------+-------+---------------+---------+---------+-------+------+----------+-------+
| id | select_type | table   | partitions | type  | possible_keys | key     | key_len | ref   | rows | filtered | Extra |
+----+-------------+---------+------------+-------+---------------+---------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | student | NULL       | const | PRIMARY       | PRIMARY | 4       | const |    1 |   100.00 | NULL  |
+----+-------------+---------+------------+-------+---------------+---------+---------+-------+------+----------+-------+
1 row in set, 1 warning

+----+-------------+---------+------------+------+---------------+------+---------+------+------+----------+-------------+
| id | select_type | table   | partitions | type | possible_keys | key  | key_len | ref  | rows | filtered | Extra       |
+----+-------------+---------+------------+------+---------------+------+---------+------+------+----------+-------------+
|  1 | SIMPLE      | student | NULL       | ALL  | NULL          | NULL | NULL    | NULL |   12 |    10.00 | Using where |
+----+-------------+---------+------------+------+---------------+------+---------+------+------+----------+-------------+

Searching by sid (the primary key) uses the index (type = const, key = PRIMARY). Searching by name, which has no index, reads all 12 rows (type = ALL). Create an index and ask again:

SQL
CREATE INDEX idx_student_name ON student (name);
EXPLAIN SELECT * FROM student WHERE name = 'Ada Lovelace';
DROP INDEX idx_student_name ON student;
Output (MySQL 8.4)
+----+-------------+---------+------------+------+------------------+------------------+---------+-------+------+----------+-------+
| id | select_type | table   | partitions | type | possible_keys    | key              | key_len | ref   | rows | filtered | Extra |
+----+-------------+---------+------------+------+------------------+------------------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | student | NULL       | ref  | idx_student_name | idx_student_name | 242     | const |    1 |   100.00 | NULL  |
+----+-------------+---------+------------+------+------------------+------------------+---------+-------+------+----------+-------+
1 row in set, 1 warning

Now type = ref and key = idx_student_name: MySQL looks the name up in the index and reads one row. With 12 rows you would never notice the difference; with 12 million you would. How indexes work, and when they help, is the subject of Module 9.

EXPLAIN FORMAT=TREE prints the same plan as a tree that is easier to read for joins. The cost numbers are internal estimates and differ between MySQL versions, so compare plans on your server rather than with the numbers printed here.

SQL
EXPLAIN FORMAT=TREE
SELECT s.name, c.title
FROM student s
JOIN enrollment e ON e.sid = s.sid
JOIN course c ON c.course_id = e.course_id
WHERE s.sid = 3\G
Output (MySQL 8.4)
*************************** 1. row ***************************
EXPLAIN: -> Nested loop inner join  (cost=1.61 rows=3)
    -> Covering index lookup on e using PRIMARY (sid=3)  (cost=0.561 rows=3)
    -> Single-row index lookup on c using PRIMARY (course_id=e.course_id)  (cost=0.283 rows=1)

1 row in set

Habits that make queries faster and safer

  • Select only the columns you need, instead of SELECT *.
  • Filter as early as possible with WHERE, and put row conditions in WHERE rather than HAVING.
  • Join on indexed columns (primary and foreign keys). MySQL creates an index for every foreign key automatically.
  • Avoid wrapping an indexed column in a function in WHERE, such as WHERE YEAR(joined) = 2026; the index cannot be used. Compare the bare column with a range instead. (Module 9 explains why.)
  • Do not use DISTINCT to hide duplicates that a wrong join created. Fix the join.
  • Use LIMIT while exploring big tables.
  • Measure before and after with EXPLAIN. Do not rely on folklore such as "EXISTS is always faster than IN".

MySQL or SQLite?

The lab uses SQLite, not MySQL, so you can practise anywhere. For the queries in this tutorial the two behave identically, and every challenge below was checked to give the same answer on both. Differences you may notice:

  • SQLite shows 3.9 where MySQL shows 3.90 (it does not keep trailing zeros in DECIMAL columns).
  • There is no SHOW TABLES or DESCRIBE. Use SELECT name FROM sqlite_master WHERE type='table'; and PRAGMA table_info(student);.
  • Error messages are worded differently. The ideas (syntax error, unknown column, constraint failed) are the same.
  • Use || to join text. Recent SQLite also accepts CONCAT(), but older versions do not.
  • SQLite supports FULL OUTER JOIN (since 3.39); MySQL does not, so do not rely on it when you move back to MySQL.
