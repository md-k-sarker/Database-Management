Alternative Database Systems

You already know MySQL. Here you install three more engines, load the same small music database into each, and learn how to choose between them. Every step says what to type and what you should see.

Lab 1 · 40 minSQLiteA database in a single file. Install, load data, query, break things safely. Lab 2 · 50 minPostgreSQLA full server. Roles, strict types, JSON, two-session transactions, backups. Lab 3 · 40 minMongoDBDocuments instead of rows. Insert, query, aggregate, index, validate. Lab 4 · 20 minDecideScenario challenge, decision wizard and a short written recommendation.

Before you start

  • A computer where you can install software (administrator rights) and about 3 GB of free disk space.
  • A terminal and a plain text editor. Docker Desktop is optional; it gives a second way to run PostgreSQL and MongoDB without installing them.
  • The SQL you learned in Module 4. Nothing in Lab 1 or Lab 2 asks for more.

How to open a terminal

Press the Windows key, type PowerShell, press Enter. All Windows commands here are written for PowerShell.

Press Command + Space, type Terminal, press Enter.

Press Ctrl + Alt + T, or open Terminal from your applications menu.

How to use this playbook

  • Pick your operating system in the left rail. Install steps and commands adjust to it.
  • Use the Copy button on any code block, then paste into your terminal or database shell.
  • Open Expected output after you run a command to check your result. Small differences (timestamps, spacing, row order without ORDER BY) are normal.
  • Tick Done on each step. The bars in the rail fill up and your place is remembered in this browser.
  • Three kinds of input look alike but are not the same: SQL statements end with ;, SQLite shell commands start with . (like .tables), and psql commands start with \ (like \dt). The dot and backslash commands take no semicolon.
Type the commands instead of only pasting them at least once per lab. Your fingers learn the syntax faster than your eyes.

One dataset, three engines

All labs use a tiny music library: 5 artists, 8 albums, 20 tracks. In SQLite and PostgreSQL it becomes three related tables. In MongoDB the same facts become one document per artist with albums and tracks nested inside. The track lengths and prices are illustrative data made up for this exercise.

artist

  • artist_id (key)
  • name
  • genre

album

  • album_id (key)
  • title
  • release_year
  • artist_id (foreign key)

track

  • track_id (key)
  • title
  • album_id (foreign key)
  • seconds
  • price

One artist has many albums, and one album has many tracks. Keep this shape in mind: the labs show how each engine stores it.

Where does each engine live?

SQLite

Your program+SQLite library→music.db file

The engine is a library inside your program. No server and no network. The database is a file you can copy.

PostgreSQL

Client (psql, app)→ port 5432 →Server process→Data directory

A server runs all the time. Clients log in as roles and send SQL over the network.

MongoDB

Client (mongosh, app)→ port 27017 →mongod server→Collections of documents

Also a server, but it stores flexible JSON-like documents instead of table rows.

Lab 1 · about 40 minutes

SQLite: a database in one file

SQLite is the most widely deployed database in the world because it needs no server. The whole database is one file that your program opens directly. You will install it, build the music database, and then poke at its unusual habits on purpose.

By the end of this lab you can

  • Install SQLite and open, create and inspect a database from the sqlite3 shell.
  • Run joins, aggregates and window functions you know from MySQL.
  • Explain SQLite's flexible typing, why foreign keys must be switched on, and what a query plan shows.
  • Import and export CSV, call SQLite from Python, and explain why concurrent writers are its weak spot.
  1. Open sqlite.org/download.html. Under Precompiled Binaries for Windows, download the sqlite-tools-win-x64 zip. It contains sqlite3.exe.
  2. Create the folder C:\sqlite and extract the zip into it.
  3. Tell PowerShell where it is, for this window only:
$env:Path += ";C:\sqlite"

Your turn

  1. List tracks longer than 500 seconds with their album title, longest first.
  2. Count albums per genre, most albums first (break ties by genre name).

SELECT t.title, al.title AS album, t.seconds

-- 2
SELECT ar.genre, COUNT(*) AS albums

-- 3
SELECT al.title, COUNT(*) AS n
FROM album al JOIN track t USING (album_id)
GROUP BY al.album_id

MySQL and PostgreSQL reject a word in an integer column. SQLite gives each column a type affinity, a preference, not a rule. Watch what happens:

SELECT typeof(1), typeof(1.5), typeof('a'), typeof(NULL);

CREATE TABLE demo (x INTEGER);
INSERT INTO demo VALUES ('abc');
INSERT INTO demo VALUES ('42');
SELECT x, typeof(x) FROM demo;
Expected output
typeof(1)  typeof(1.5)  typeof('a')  typeof(NULL)
---------  -----------  -----------  ------------
integer    real         text         null

x    typeof(x)
---  ---------
abc  text
42   integer

The text '42' was converted to the integer 42 because it looks like a number. The text 'abc' was stored as text inside an INTEGER column. Now try a STRICT table, which enforces types the way PostgreSQL does:

CREATE TABLE demo_strict (x INTEGER) STRICT;
INSERT INTO demo_strict VALUES ('abc');
Expected output
Runtime error: cannot store TEXT value in INTEGER column demo_strict.x (19)

Clean up:

DROP TABLE demo;
DROP TABLE demo_strict;
Flexible typing is convenient for prototypes and a trap for production data. If you want the database to protect you, declare tables STRICT.

Zero means off. SQLite will happily accept an album whose artist does not exist:

INSERT INTO album (title, release_year, artist_id) VALUES ('Ghost Album', 2020, 99);
SELECT title, artist_id FROM album WHERE artist_id = 99;
DELETE FROM album WHERE title = 'Ghost Album';
Expected output of the SELECT
title        artist_id
-----------  ---------
Ghost Album  99

Switch enforcement on and repeat the insert:

PRAGMA foreign_keys = ON;
INSERT INTO album (title, release_year, artist_id) VALUES ('Ghost Album', 2020, 99);
Expected output
Runtime error: FOREIGN KEY constraint failed (19)

The CHECK constraint from your schema is always active:

INSERT INTO track (title, album_id, seconds) VALUES ('Zero', 1, 0);
Expected output
Runtime error: CHECK constraint failed: seconds > 0 (19)
PRAGMA foreign_keys = ON applies to one connection only. Every program that opens the database must run it again, or foreign keys are silently ignored.

The shell runs each statement on its own unless you open a transaction. Change every price, look, then roll back:

BEGIN;
UPDATE track SET price = 1.99;
SELECT DISTINCT price FROM track ORDER BY price;
ROLLBACK;
SELECT DISTINCT price FROM track ORDER BY price;
Expected output
price
-----
1.99

price
-----
0.99
1.29

Inside the transaction every price was 1.99. After ROLLBACK the original prices are back. Replace ROLLBACK with COMMIT and the change would be permanent. Module 10 covers this in depth.

Ask SQLite how it would find the tracks of album 3:

EXPLAIN QUERY PLAN SELECT * FROM track WHERE album_id = 3;
Expected output
QUERY PLAN
`--SCAN track

SCAN means it reads every row. Add an index and ask again:

CREATE INDEX idx_track_album ON track(album_id);
EXPLAIN QUERY PLAN SELECT * FROM track WHERE album_id = 3;
Expected output
QUERY PLAN
`--SEARCH track USING INDEX idx_track_album (album_id=?)

SEARCH ... USING INDEX jumps straight to the matching rows. With 20 rows you will not feel a difference, with 20 million you would. Module 9 returns to indexing.

Python ships with the sqlite3 module, so no install is needed. Save this as use_sqlite.py in the same folder as music.db.

import sqlite3

con = sqlite3.connect("music.db")
con.execute("PRAGMA foreign_keys = ON")   # per connection, remember?
con.row_factory = sqlite3.Row

sql = """
SELECT ar.name, COUNT(*) AS tracks
FROM track t
JOIN album al  ON al.album_id  = t.album_id
JOIN artist ar ON ar.artist_id = al.artist_id
GROUP BY ar.name
ORDER BY tracks DESC, ar.name
"""
for row in con.execute(sql):
    print(row["name"], row["tracks"])

# Parameterized query: the ? is filled in safely. Never build SQL with f-strings.
min_seconds = 400
rows = con.execute(
    "SELECT title FROM track WHERE seconds > ? ORDER BY title", (min_seconds,)
).fetchall()
print([r["title"] for r in rows])

con.close()

SQLite allows many readers but only one writer at a time. Prove it with two terminals in the same db-lab folder.

Terminal A

sqlite3 music.db
BEGIN IMMEDIATE;
UPDATE track SET price = 1.49 WHERE track_id = 1;

Leave this terminal as it is: the transaction is still open.

Terminal B

sqlite3 music.db
UPDATE track SET price = 1.59 WHERE track_id = 2;
Expected output in Terminal B
Runtime error: database is locked (5)

Back in Terminal A

ROLLBACK;

Now repeat the update in Terminal B. It succeeds. Restore the price it changed:

UPDATE track SET price = 0.99 WHERE track_id = 2;

Write-ahead logging

PRAGMA journal_mode;
PRAGMA journal_mode = WAL;
Expected output
delete
wal

WAL mode lets readers keep reading while one writer writes. It is still one writer at a time. PostgreSQL, in Lab 2, lets many sessions write to different rows at once.

Because the database is a file, a backup is a copy. The shell offers two safe ways:

.backup music_backup.db
.output music_dump.sql
.dump
.output stdout

.backup makes a binary copy. .dump writes plain SQL text that recreates everything; open music_dump.sql to read it. That is SQLite's version of mysqldump. Type .quit when you are done.

Check the files exist
music.db  music_backup.db  music_dump.sql  artists.csv  use_sqlite.py

Install DB Browser for SQLite, choose Open Database, and pick music.db. Browse the tables on the Browse Data tab and run a query on Execute SQL. Close the tool before running anything that writes from the shell, or you may hit a lock like the one in step 13.

Takeaways

  • SQLite is a library plus a file. Zero setup makes it ideal for local apps, prototypes, tests and teaching.
  • Most of your SQL works unchanged. Watch for flexible typing, off-by-default foreign keys, and PRAGMA.
  • One writer at a time makes it a poor fit for busy multi-user servers.

PostgreSQL: the open-source workhorse

PostgreSQL is a real database server. It runs all the time, logs clients in as roles, enforces types strictly, and lets many sessions work at once. You will install it, load the same music database, and see what a server gives you that a file does not.

By the end of this lab you can

  • Install PostgreSQL, connect with psql, and create roles and databases.
  • Port MySQL and SQLite SQL to PostgreSQL syntax.
  • Store and query JSON with JSONB, and use CTEs and window functions.
  • Demonstrate concurrent transactions from two sessions, read a query plan, restrict a role with GRANT, and back up with pg_dump.

Your 20-row tables are too small for the planner to bother with indexes. Build a bigger table, ask for a plan, add an index, ask again:

CREATE TABLE big AS
  SELECT g AS id, (random() * 1000)::int AS k
  FROM generate_series(1, 200000) AS g;

EXPLAIN ANALYZE SELECT * FROM big WHERE k = 42;

CREATE INDEX big_k ON big (k);
ANALYZE big;

EXPLAIN ANALYZE SELECT * FROM big WHERE k = 42;

DROP TABLE big;

The exact numbers are yours alone, but look for these signs:

  • Before the index: a Seq Scan (or Parallel Seq Scan) on big with a large Rows Removed by Filter, and an execution time of a few to tens of milliseconds.
  • After the index: a Bitmap Index Scan on big_k or an Index Scan, and a much smaller execution time, typically under a millisecond.
EXPLAIN ANALYZE actually runs the query. Be careful using it on statements that change data.

You embedded albums and tracks inside each artist. Another design keeps tracks in their own collection and links to them by ID or name. Neither is always right. Use these questions:

QuestionLean toward embeddingLean toward referencing
How is it read?Almost always together with the parentOften on its own
How many children?A small, bounded numberUnbounded or very large (a document is limited to 16 MB)
How often does a child change?RarelyConstantly, from many writers
Is the child shared?No, it belongs to one parentYes, many parents point to it

Try it: listeners press play thousands of times a day. Would you store each play event inside the track, or in a separate collection?

Show the reasoning

A separate collection. Play events are unbounded, arrive constantly from many writers, and are usually analysed on their own. Embedding them would grow every track document without limit and make each play rewrite a large document. Album and track details, by contrast, are small, stable and almost always read with their artist, so embedding them is reasonable.

Troubleshooting

Read the error message first. It usually names the problem.

SQLite

sqlite3 is not recognized (Windows) or command not found

The folder that holds sqlite3.exe is not on your PATH. On Windows run $env:Path += ";C:\sqlite" in that PowerShell window, or use the full path such as C:\sqlite\sqlite3.exe music.db. On Linux install the package from step 1.

Error: no such table: track

You opened a different or empty database file. Check where you are with pwd (or cd on Windows) and run .databases to see which file the shell has open. Run sqlite3 music.db from the db-lab folder.

Runtime error: database is locked (5)

Another connection holds a write lock. Close other shells, viewers such as DB Browser, or commit or roll back an open transaction. In the shell, .timeout 3000 makes it wait up to three seconds before giving up.

My foreign key errors never appear

Foreign keys are off by default for each connection. Run PRAGMA foreign_keys = ON; every time you connect.

PostgreSQL

connection to server ... failed: Connection refused

The server is not running or is on another port. Windows: open Services and start the postgresql service. macOS Homebrew: brew services start postgresql@18 (use your version). Linux: sudo systemctl start postgresql. Docker: docker start pg-lab.

password authentication failed for user

Wrong password. For the roles in this lab: student uses lab_pass, reader uses read_only_pw, and the postgres password is the one you chose during install (labpass for the Docker command above).

Peer authentication failed (Linux)

Connecting through the local socket makes PostgreSQL compare your Linux username with the role name. Add -h localhost to force a password login over the network, or use sudo -u postgres psql for the administrator.

FATAL: database "music" does not exist, or role "student" does not exist

Run the create statements from step 4 in an administrator session, then reconnect. Check what exists with \l and \du.

psql is not recognized (Windows)

Add the bin folder of your installation to the PATH for this window, for example $env:Path += ";C:\Program Files\PostgreSQL\18\bin", or use SQL Shell (psql) from the Start menu.

relation "track" already exists

You ran the create script twice. Either continue with the data you have, or start fresh: DROP TABLE track_meta, track, album, artist; and run the script again.

MongoDB

connect ECONNREFUSED 127.0.0.1:27017

The mongod server is not running. Windows: start the MongoDB Server service in Services. macOS: brew services start mongodb-community. Linux: sudo systemctl start mongod. Docker: docker start mongo-lab.

mongosh is not recognized

The shell is a separate install on Windows. Download MongoDB Shell, install it, and open a new terminal window. On macOS use brew install mongosh.

My query returns nothing

Check db to confirm you are in music, run show collections to confirm artists exists, and check spelling and capitalization: field names and string values are case-sensitive.

Pasting multi-line code shows errors

Paste the whole block at once rather than line by line. If it still fails, paste it into a text file first, check for smart quotes or stray characters, and copy from there. Alternatively save it as load.js and run load("load.js") in mongosh.
