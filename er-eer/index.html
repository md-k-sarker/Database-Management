1. Entities, attributes, relationships, and participation

By the end you can read a paragraph of requirements and sketch a correct ER diagram, including how many and how strongly things relate.

Theory

Why we model before we build

Database design moves through four stages. ER diagrams belong to the second one, the conceptual design: a picture that people who do not write SQL can still check against reality.

  1. Requirements: what the organization needs to store and ask.
  2. Conceptual design: the ER or EER diagram.
  3. Logical design: the relational schema (tables, keys).
  4. Physical design: indexes, storage, tuning.

A mistake caught in stage 2 costs a pencil eraser. The same mistake caught after the application ships costs a migration.

Reading trick. In requirement text, nouns usually become entities, verbs become relationships, and descriptive details become attributes. Numbers like "exactly one" and "at least one" become constraints.

Theory

Entities and attributes

An entity is a thing we keep facts about (a student, a course). An entity type is the template; an entity instance is one real student. An attribute is a fact about the entity.

Attribute kindMeaningExampleDrawn as
SimpleCannot be divided furtheremailOval

MultivaluedSeveral values at oncephone numbersDouble oval

A key must be unique, stable, and as small as possible. An email is unique but people change it; a name is not unique at all. That is why a system-assigned ID usually wins.

Theory

Relationships, cardinality, and participation

A relationship associates entities. Its degree is how many entity types take part: unary (one, e.g. an employee supervises an employee), binary (two, the most common), ternary (three).

Cardinality ratio says how many instances can be on each side:

  • 1:1: one student has at most one ID card, and each card belongs to one student.
  • 1:N: one department has many instructors, but each instructor works in one department.
  • M:N: students take many courses, and courses have many students.

Participation says whether taking part is required. Total (double line): every instance must participate, for example every instructor must work in a department. Partial (single line): participation is optional, for example a department may exist before it has any instructors.

Where attributes of a relationship live. A grade depends on both the student and the course. It belongs to the relationship ENROLLS_IN, not to STUDENT or COURSE.

Some textbooks write cardinality as a (min, max) pair on each line, such as (1, N). Min 1 means total participation, min 0 means partial. Same information, different handwriting.

Example

Weak entities and identifying relationships

A weak entity has no key of its own. A dependent's name is only unique within one instructor's family, so a DEPENDENT is identified by the owner's key plus a partial key. The relationship that connects them is an identifying relationship (double diamond), and the weak entity always participates totally.

2. Extended ER: specialization and generalization

Model "is a" hierarchies: when a group of entities shares some facts but also has facts of its own.

Theory

Superclasses, subclasses, and inheritance

Sometimes one entity type hides several flavors. Every STUDENT and every INSTRUCTOR is a PERSON, but only students have a GPA and only instructors have a salary. EER lets us draw that.

  • Superclass: the general type (PERSON).
  • Subclass: a specific type (STUDENT). Each subclass instance is one instance of the superclass.
  • Inheritance: a subclass automatically has all attributes and relationships of its superclass, plus its own local ones.

Specialization works top-down: you start with PERSON and notice that subgroups need their own attributes. Generalization works bottom-up: you start with CAR and TRUCK, notice they share plate number and year, and factor out VEHICLE. Same diagram, different direction of thought.

Theory

Two constraints on every specialization

Disjointness
Can one entity belong to more than one subclass?
Disjoint (d): at most one. Overlapping (o): possibly several.
Completeness
Must every superclass entity belong to some subclass?
Total (double line): yes. Partial (single line): no.

That gives four combinations. A subclass can also have subclasses of its own, forming a hierarchy (below, STUDENT splits into UNDERGRAD and GRADUATE). When a subclass has several superclasses, you have a lattice. A category (union type) is the opposite situation: one subclass whose members come from different superclasses, such as an OWNER that can be a PERSON or a COMPANY.

Theory

Four ways to map a specialization

Mapping is a design decision, not a formula. These are the standard options (we number them 8A to 8D, following the usual textbook rule 8):

OptionHow it worksBest whenWatch out for
8A: superclass and subclass tablesOne table for the superclass; one per subclass whose key is also a foreign key to the superclass.Any case, and the only clean choice for overlapping, partial hierarchies.Reading a full subclass row needs a join.
8B: subclass tables onlyNo superclass table; every subclass table repeats the superclass attributes.Disjoint and total, with queries that rarely span subclasses.Duplicated columns; overlapping entities are stored twice.
8C: single table with a type columnOne wide table; a type column says which subclass.Disjoint, few subclass-specific attributes.Many NULLs when subclasses differ a lot.
8D: single table with Boolean flagsOne wide table with one yes/no column per subclass.Overlapping, few local attributes.Lots of NULLs; flags and local columns can drift out of sync.
Run it

Option 8A and 8C in one schema

PERSON, STUDENT, and INSTRUCTOR use 8A because they overlap and are partial. Inside STUDENT, the disjoint and total split into UG and GR uses 8C with a type column and a CHECK constraint that keeps the local attributes honest.

Lab 2: specialization mapping
PRAGMA foreign_keys = ON;
DROP TABLE IF EXISTS instructor;
DROP TABLE IF EXISTS student;
DROP TABLE IF EXISTS person;

CREATE TABLE person (
  pid   INTEGER PRIMARY KEY,
  name  TEXT NOT NULL,
  email TEXT UNIQUE
);

-- 8A subclass tables: key is also a foreign key to the superclass
CREATE TABLE student (
  pid          INTEGER PRIMARY KEY REFERENCES person(pid) ON DELETE CASCADE,
  gpa          REAL CHECK (gpa BETWEEN 0 AND 4),
  level        TEXT NOT NULL CHECK (level IN ('UG', 'GR')),  -- 8C: disjoint + total
  class_year   INTEGER,        -- UG only
  thesis_title TEXT,           -- GR only
  CHECK ( (level = 'UG' AND thesis_title IS NULL)
       OR (level = 'GR' AND class_year   IS NULL) )
);

CREATE TABLE instructor (
  pid      INTEGER PRIMARY KEY REFERENCES person(pid) ON DELETE CASCADE,
  job_rank TEXT,
  salary   INTEGER
);

INSERT INTO person VALUES (1, 'Ada',   'ada@example.edu'),
                          (2, 'Ben',   'ben@example.edu'),
                          (3, 'Carla', 'carla@example.edu'),
                          (4, 'Dev',   'dev@example.edu');
INSERT INTO student    VALUES (1, 3.8, 'UG', 3, NULL),
                              (2, 3.6, 'GR', NULL, 'Explainable GNNs');
INSERT INTO instructor VALUES (2, 'Teaching assistant', 18000),   -- Ben is BOTH: overlapping
                              (3, 'Associate', 90000);

-- Dev is neither student nor instructor: the specialization is partial
SELECT p.name,
       (s.pid IS NOT NULL) AS is_student,
       (i.pid IS NOT NULL) AS is_instructor
FROM person p
LEFT JOIN student s    ON s.pid = p.pid
LEFT JOIN instructor i ON i.pid = p.pid
ORDER BY p.pid;

3. Converting ER and EER diagrams to relational schemas

Apply the standard mapping algorithm step by step, and finish with a runnable schema of a whole campus.

Theory

The big idea

Every ER construct has a standard relational home. Learn these eight rules and you can convert any diagram.

ER constructRelational result
Regular entityA table; simple attributes become columns; the key becomes the primary key.
Weak entityA table with a foreign key to its owner; primary key = owner key + partial key.
1:1 relationshipForeign key (UNIQUE) on one side, preferably the total-participation side.
1:N relationshipForeign key on the N side.
M:N relationshipNew table holding both keys (plus relationship attributes); primary key = both keys.
Multivalued attributeNew table: owner key + the value; primary key = both.
N-ary relationshipNew table with a foreign key to every participant.
SpecializationOptions 8A to 8D (module 2).

PRAGMA foreign_keys = ON;
DROP TABLE IF EXISTS teaches;       DROP TABLE IF EXISTS enrollment;
DROP TABLE IF EXISTS student_phone; DROP TABLE IF EXISTS undergrad;
DROP TABLE IF EXISTS graduate;      DROP TABLE IF EXISTS id_card;
DROP TABLE IF EXISTS dependent;     DROP TABLE IF EXISTS semester;
DROP TABLE IF EXISTS course;        DROP TABLE IF EXISTS student;
DROP TABLE IF EXISTS instructor;    DROP TABLE IF EXISTS department;

-- Rule 1: regular entities
CREATE TABLE department (dno INTEGER PRIMARY KEY, dname TEXT NOT NULL UNIQUE, office TEXT);
CREATE TABLE student    (sid INTEGER PRIMARY KEY, name TEXT NOT NULL, email TEXT NOT NULL UNIQUE);
CREATE TABLE course     (code TEXT PRIMARY KEY, title TEXT NOT NULL,
                         credits INTEGER NOT NULL CHECK (credits > 0));
CREATE TABLE semester   (term_id TEXT PRIMARY KEY, start_date TEXT);

-- Rule 4: WORKS_FOR is 1:N, so the foreign key goes on the N side (total => NOT NULL)
CREATE TABLE instructor (
  iid INTEGER PRIMARY KEY, name TEXT NOT NULL, job_rank TEXT,
  dno INTEGER NOT NULL REFERENCES department(dno)
);

-- Rule 2: weak entity. PK = owner key + partial key; delete the owner, delete the dependents
CREATE TABLE dependent (
  iid INTEGER NOT NULL REFERENCES instructor(iid) ON DELETE CASCADE,
  dep_name TEXT NOT NULL, relationship TEXT,
  PRIMARY KEY (iid, dep_name)
);

-- Rule 3: 1:1 HAS. FK on the total side (every card has a student), UNIQUE enforces 1:1
CREATE TABLE id_card (
  card_no INTEGER PRIMARY KEY, issued_on TEXT,
  sid INTEGER NOT NULL UNIQUE REFERENCES student(sid)
);

-- Rule 5: M:N ENROLLS_IN becomes a table; the relationship attribute (grade) rides along
CREATE TABLE enrollment (
  sid  INTEGER REFERENCES student(sid),
  code TEXT    REFERENCES course(code),
  grade TEXT,
  PRIMARY KEY (sid, code)
);

-- Rule 6: multivalued attribute phone
CREATE TABLE student_phone (
  sid INTEGER REFERENCES student(sid) ON DELETE CASCADE,
  phone TEXT,
  PRIMARY KEY (sid, phone)
);

-- Rule 7: ternary TEACHES (instructor, course, semester)
CREATE TABLE teaches (
  iid INTEGER REFERENCES instructor(iid),
  code TEXT REFERENCES course(code),
  term_id TEXT REFERENCES semester(term_id),
  PRIMARY KEY (iid, code, term_id)
);

-- Rule 8 (option 8A): specialization of STUDENT
CREATE TABLE undergrad (sid INTEGER PRIMARY KEY REFERENCES student(sid) ON DELETE CASCADE, class_year INTEGER);
CREATE TABLE graduate  (sid INTEGER PRIMARY KEY REFERENCES student(sid) ON DELETE CASCADE, thesis_title TEXT);

Common mistakes. (1) Putting the foreign key on the 1 side of a 1:N. (2) Forgetting that a junction table's primary key must be the pair, not each key alone. (3) Storing a multivalued attribute as a comma-separated string. (4) Giving a weak entity its own auto-number key and dropping the owner link. (5) Treating a ternary relationship as three binary ones, which loses which combination actually happened.

When the pair is not enough. If a student could take the same course twice (a retake), (sid, code) would block the second row. Add the semester to the key, or turn ENROLLMENT into an entity with its own ID. Requirements decide, not habit.

4. Justifying design choices

A diagram is an argument. Learn the principles that make one design better than another, and how to say why.

Theory

Principles you can cite

  1. Faithfulness. The model says what the requirements say, no more and no less. Every entity, line, and constraint traces back to a sentence.
  2. No redundancy. Store each fact once. Duplicated facts cause update, insertion, and deletion anomalies (you will run all three below).
  3. Entity or attribute? Promote an attribute to an entity when it has attributes of its own, takes part in relationships, or has several values. A city with a state and a population is an entity; a street number is an attribute.
  4. Entity or relationship? If a "relationship" needs its own relationships (a registration that has payments), turn it into an entity.
  5. Binary or ternary? Use a ternary relationship only when the three-way combination carries meaning that three binary ones would lose.
  6. Key choice. Prefer stable, unique, short keys. Use a surrogate key (system-generated ID) when the natural key is long, changeable, or not truly unique.
  7. Normal forms. A faithful ER design converted by the rules above tends to land in 3NF or BCNF: every non-key attribute depends on the key, the whole key, and nothing but the key.
  8. Trade-offs, stated. Denormalizing can speed up reads, but you owe a note on what you duplicated and how you will keep it consistent.
Theory

How to write a justification

A strong justification has three parts: requirement (what the situation demands), principle (which rule applies), and trade-off (what you accept in return).

WeakStrong
"I made ENROLLMENT a table because that is how you do M:N.""Students take many courses and courses have many students (M:N), and a grade depends on both. A junction table stores each fact once and keeps the grade with the pair. The cost is one extra join when listing a student's courses."

  sid INTEGER, student_name TEXT, course_code TEXT, course_title TEXT, instructor_name TEXT, grade TEXT
);
INSERT INTO flat_enrollment VALUES
  (1, 'Ada Lovelace', 'COSC214', 'Data Structures',     'Dr. Rivera', 'A'),
  (2, 'Ben Carter',   'COSC214', 'Data Structures',     'Dr. Rivera', 'A'),
  (1, 'Ada Lovelace', 'COSC431', 'Database Management', 'Dr. Okafor', 'B');

-- UPDATE anomaly: rename the course, but only one row gets changed
UPDATE flat_enrollment SET course_title = 'Data Structures and Algorithms'
WHERE sid = 1 AND course_code = 'COSC214';
SELECT DISTINCT course_code, course_title FROM flat_enrollment ORDER BY 1, 2;

-- DELETION anomaly: the last student drops COSC431 and the course itself vanishes
DELETE FROM flat_enrollment WHERE course_code = 'COSC431';
SELECT COUNT(*) AS rows_about_cosc431 FROM flat_enrollment WHERE course_code = 'COSC431';

-- INSERTION anomaly: a brand-new course with no students has nowhere to live
-- (a flat row needs a student; we would have to invent NULL students)

-- The fix: each fact stored once
DROP TABLE IF EXISTS enrollment_n; DROP TABLE IF EXISTS course_n; DROP TABLE IF EXISTS student_n;
CREATE TABLE student_n (sid INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE course_n  (code TEXT PRIMARY KEY, title TEXT NOT NULL);
CREATE TABLE enrollment_n (
  sid INTEGER REFERENCES student_n(sid), code TEXT REFERENCES course_n(code), grade TEXT,
  PRIMARY KEY (sid, code)
);
INSERT INTO student_n VALUES (1, 'Ada Lovelace'), (2, 'Ben Carter');
INSERT INTO course_n  VALUES ('COSC214', 'Data Structures'), ('COSC431', 'Database Management');

UPDATE course_n SET title = 'Data Structures and Algorithms' WHERE code = 'COSC214';   -- ONE place
INSERT INTO course_n VALUES ('COSC999', 'Brand-new Course');                           -- no students needed

SELECT s.name, c.title, e.grade
FROM enrollment_n e JOIN student_n s ON s.sid = e.sid JOIN course_n c ON c.code = e.code
