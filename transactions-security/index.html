01Start here

A transaction is a group of database operations that must succeed or fail as one unit. Moving money from one account to another is the classic example: if the system stops after taking money out of one account and before putting it into the other, the money has vanished. Transactions are how a database prevents that, even when thousands of users work at the same time.

The second half of this module is about security: deciding who may see and change which data, defending against attacks such as SQL injection, and acting responsibly with other people's information.

What you will be able to do

  • Explain ACID and show each property on a real server.
  • Use START TRANSACTION, COMMIT, ROLLBACK and savepoints correctly.
  • Predict what two sessions running at the same time will see at each isolation level, and diagnose a deadlock.
  • Give a user exactly the privileges they need, using GRANT, REVOKE, roles and views.
  • Recognize and prevent SQL injection, and store passwords properly.
  • Discuss the ethical and legal duties of a person who handles data.

Two sessions

Many of the experiments need two sessions open at once, called T1 and T2. A session is one connection to the server. In MySQL Workbench, each SQL query tab uses its own connection, so two tabs are two sessions. With the command-line client, open two terminal windows. The outputs in this module were recorded from real pairs of sessions on the server below; you will replay them step by step with a viewer in section 4.

Server settings

The server used for every example: MySQL 8.4.2, default storage engine InnoDB, default isolation level REPEATABLE-READ, autocommit = 1, innodb_lock_wait_timeout = 50 seconds. Transactions need a transactional storage engine; InnoDB is the default in MySQL 8.4.

The two halves are linked: a transaction that cannot be trusted corrupts your data by accident; a system without access control lets people corrupt or steal it on purpose.

02ACID

ACID is the set of four guarantees that a transactional database gives you. Each letter describes a different kind of failure that the database protects you from.

LetterPropertyPlain meaningProtects against
AAtomicityAll the statements of a transaction take effect, or none do.A crash or error half-way through a transfer
CConsistencyA transaction takes the database from one valid state to another; constraints are never left violated.Data that breaks the rules (negative balance, orphan rows)
IIsolationConcurrent transactions do not see each other's unfinished work; the result is as if they ran one at a time, to the degree the isolation level promises.Two users interfering with each other
DDurabilityOnce COMMIT returns, the change survives a crash or power loss.Losing committed work

Atomicity in action

Move 300 from Alice to Bob. This takes two UPDATE statements. The widget below replays what happened on the real server when the connection to the database was lost between the two statements, with and without a transaction.

Without a transaction, every statement is committed on its own (this is autocommit mode, the MySQL default), so the debit is permanent even though the credit never happened. With a transaction, the server rolled back the unfinished work as soon as the connection dropped.

Consistency in action

The account table has a rule: CHECK (balance >= 0). Watch what happens when a transaction tries to break it. Notice carefully what is undone: only the failing statement. The earlier UPDATE in the same transaction is still in effect until you decide to roll back.

Transcript (one session on MySQL 8.4)
T1> START TRANSACTION
    OK

T1> UPDATE account SET balance = balance - 300 WHERE id = 1
    Query OK, 1 row affected

T1> UPDATE account SET balance = balance - 5000 WHERE id = 2
    ERROR 3819: Check constraint 'balance_not_negative' is violated.

T1> SELECT id, balance FROM account ORDER BY id
    id | balance
    ---+--------
    1  | 700    
    2  | 1000   

T1> ROLLBACK
    OK

T1> SELECT id, balance FROM account ORDER BY id
    id | balance
    ---+--------
    1  | 1000   
    2  | 1000
Statement versus transaction

An error does not end a transaction in MySQL. After a failed statement, your code must decide whether to ROLLBACK the whole transaction or carry on. Forgetting this is a common bug. (Deadlocks are different: the server rolls back the whole transaction for you. See section 6.)

Durability in action

When you commit, InnoDB writes the change to its redo log and, with the default setting, forces that log to disk before COMMIT returns. After a crash the server replays the log, so committed work is not lost. The setting that controls it:

SQL
SELECT @@innodb_flush_log_at_trx_commit;
Output (MySQL 8.4)
+----------------------------------+
| @@innodb_flush_log_at_trx_commit |
+----------------------------------+
|                                1 |
+----------------------------------+
1 row in set

The value 1 is the default and the only setting that gives full ACID durability. Values 0 and 2 are faster but can lose the most recent transactions in a crash. You will not change this in this course, but you should know it exists.

Isolation is the tricky one

Atomicity, consistency and durability are about one transaction. Isolation is about what happens when several run at once, and it comes in levels because perfect isolation costs performance. Sections 4 to 6 cover it in depth.

03Controlling transactions

Four statements control a transaction. Learn them, and the one setting that decides whether you are in one without knowing it.

Autocommit

By default MySQL is in autocommit mode: every statement is its own transaction that commits immediately. That is convenient, and it is why a lone UPDATE cannot be undone.

SQL
SELECT @@autocommit;
Output (MySQL 8.4)
+--------------+
| @@autocommit |
+--------------+
|            1 |
+--------------+
1 row in set

The control statements

StatementWhat it does
START TRANSACTION (or BEGIN)Starts a transaction. Autocommit is suspended until the transaction ends.
COMMITMakes all changes since the start permanent and visible to others.
ROLLBACKUndoes all changes since the start.
SAVEPOINT name / ROLLBACK TO SAVEPOINT nameMarks a point inside a transaction that you can return to without abandoning the whole transaction.
SET autocommit = 0Makes every statement part of a transaction until you COMMIT or ROLLBACK. Easy to forget; the next section shows why that is dangerous.

A savepoint

Debit Alice, make a mistake crediting Bob, go back to the savepoint, and credit the right amount. Only the mistake is undone.

SQL
START TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE id = 1;
SAVEPOINT after_debit;
UPDATE account SET balance = balance + 999 WHERE id = 2;   -- oops, wrong amount
ROLLBACK TO SAVEPOINT after_debit;
UPDATE account SET balance = balance + 100 WHERE id = 2;
SELECT id, owner, balance FROM account;
COMMIT;
Output (MySQL 8.4)
+----+-------+---------+
| id | owner | balance |
+----+-------+---------+
|  1 | Alice |     900 |
|  2 | Bob   |    1100 |
+----+-------+---------+
2 rows in set

Things that end a transaction when you do not expect it

DDL statements such as CREATE TABLE and DROP TABLE cause an implicit commit. Here the ROLLBACK finds nothing to undo, because the insert was already committed:

Transcript (one session on MySQL 8.4)
T1> START TRANSACTION
    OK

T1> INSERT INTO orders VALUES (5, 'Cy', 99)
    Query OK, 1 row affected

T1> CREATE TABLE scratch (x INT)
    OK

T1> ROLLBACK
    OK

T1> SELECT id, customer FROM orders WHERE id = 5
    id | customer
    ---+---------
    5  | Cy      

T1> DROP TABLE scratch
    OK

Not every table can roll back, either. Only transactional storage engines (InnoDB, the default) can. A table in the old MyISAM engine ignores ROLLBACK, and MySQL warns you:

SQL
CREATE TABLE log_myisam (id INT PRIMARY KEY, note VARCHAR(20)) ENGINE=MyISAM;
START TRANSACTION;
INSERT INTO log_myisam VALUES (1, 'hello');
ROLLBACK;
SHOW WARNINGS;
SELECT * FROM log_myisam;
DROP TABLE log_myisam;
Output (MySQL 8.4)
+---------+------+---------------------------------------------------------------+
| Level   | Code | Message                                                       |
+---------+------+---------------------------------------------------------------+
| Warning | 1196 | Some non-transactional changed tables couldn't be rolled back |
+---------+------+---------------------------------------------------------------+
1 row in set

+----+-------+
| id | note  |
+----+-------+
|  1 | hello |
+----+-------+
1 row in set
Common mistake

If you ever see ENGINE=MyISAM in a schema you did not design, remember that transactions silently do not work on it. Foreign keys are also not enforced by MyISAM.

The pattern in a program

Programs follow one shape: do the work, commit if everything worked, roll back and re-raise on any error. This Python function was run against the demo database. A transfer of 300 succeeded; a transfer of 5000 broke the CHECK constraint, so the exception caused a rollback and the first UPDATE did not stick:

Python (PyMySQL)
import pymysql

def transfer(conn, src, dst, amount):
    try:
        with conn.cursor() as cur:
            cur.execute("UPDATE account SET balance = balance - %s WHERE id = %s", (amount, src))
            cur.execute("UPDATE account SET balance = balance + %s WHERE id = %s", (amount, dst))
        conn.commit()          # make both changes permanent
    except Exception:
        conn.rollback()        # undo everything since the transaction began
        raise
Output (run against MySQL 8.4)
transfer(1 -> 2, 300):    balances [700, 1300]
transfer(1 -> 2, 5000):   raised an error (CHECK constraint); balances [700, 1300]

In Java the same shape uses connection.setAutoCommit(false), commit() and rollback(); Module 8 shows it.

04Concurrency problems

When transactions overlap, strange things can happen. There are four classic problems. For each one you can replay a real recording of two sessions on MySQL 8.4 and see exactly what each session read.

The problems

ProblemWhat happens
Dirty readT2 reads a change that T1 has not committed. If T1 rolls back, T2 acted on data that never existed.
Non-repeatable readT2 reads a row twice in one transaction and gets different values, because T1 committed a change in between.
Phantom readT2 runs the same range query twice and the second time extra rows appear (or vanish), because T1 inserted or deleted rows in between.
Lost updateT1 and T2 both read a value, both compute a new value from it, and both write. The one who writes last overwrites the other's change.

Replay a recorded run

What each isolation level showed

The table below was produced by running the three read scenarios at all four levels on the real server. At SERIALIZABLE InnoDB turns ordinary reads inside a transaction into locking reads, so the other session has to wait. For the experiment the wait was limited to 2 seconds (innodb_lock_wait_timeout = 2, instead of the default 50) so that the recording finishes quickly.

Isolation levelDirty readNon-repeatable readPhantom read
READ UNCOMMITTEDSeen: T2 read 500, a value that was rolled backSeen: 1000 then 1500Seen: count 2 then 3
READ COMMITTEDNot seen: T2 read 1000Seen: 1000 then 1500Seen: count 2 then 3
REPEATABLE READNot seen: T2 read 1000Not seen: 1000 both timesNot seen: count 2 both times

Detail worth knowing

InnoDB is stricter than the SQL standard. The standard says REPEATABLE READ may still allow phantoms; InnoDB's REPEATABLE READ uses a snapshot, so plain SELECT statements did not see the phantom in the recording above. A transaction does see the new row once it writes to the range itself. In the last scenario of the viewer, an UPDATE by T2 touches the row that T1 inserted, and a later count then includes it (count 2, then 2, then 3). Do not assume other database systems behave the same way at the same level.

05Isolation levels and locking

The isolation level is a dial between safety and speed. Higher levels prevent more problems but make sessions wait for each other more. MySQL lets you set it per session or per transaction.

The four levels

LevelIdeaCost
READ UNCOMMITTEDReads can see uncommitted changes.Almost no protection. Rarely a good idea.
READ COMMITTEDEach statement sees only data committed before it started.Non-repeatable reads and phantoms are possible. Common in other databases' defaults.
REPEATABLE READ (InnoDB default)The whole transaction sees the snapshot of the data as of its first read.Writers can still conflict; lost updates remain possible with read-then-write code.
SERIALIZABLEAs if the transactions ran one after the other.Most waiting; lock timeouts and deadlocks are more likely.

Setting the level

SQL
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT @@transaction_isolation;
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT @@transaction_isolation;
Output (MySQL 8.4)
+-------------------------+
| @@transaction_isolation |
+-------------------------+
| READ-COMMITTED          |
+-------------------------+
1 row in set

+-------------------------+
| @@transaction_isolation |
+-------------------------+
| REPEATABLE-READ         |
+-------------------------+
1 row in set

SET SESSION ... changes the level for the rest of your session. SET TRANSACTION ISOLATION LEVEL ... (without SESSION) applies only to the next transaction. SET GLOBAL ... changes the default for new connections and needs administrator rights.

How InnoDB avoids many waits: MVCC

InnoDB keeps old versions of changed rows (in the undo log). A plain SELECT reads the version of the row that was current for its snapshot, so readers do not block writers and writers do not block readers. This is called multi-version concurrency control (MVCC). That is why, in the recordings, T2's read was never held up by T1 at the lower levels.

Fixing a lost update

Plain reads come from the snapshot, so they do not protect a read-then-write sequence. There are two reliable fixes, both recorded on the real server. Replay them in the viewer from section 4 (choose a "Lost update" scenario), or read the outcome here:

ApproachHow it worksFinal balance (expected 1300)
Read, compute in the program, writeBoth sessions read 1000 and write 1100 and 1200. The last writer wins.1200
Fix 1. Let the database compute: SET balance = balance + 100The update locks the row and uses the current value. The second session waits for the first.1300
Fix 2. SELECT ... FOR UPDATE, then updateThe first read locks the row. The second session's locking read waits, then sees the committed 1100.1300

SELECT ... FOR UPDATE takes an exclusive lock on the rows it reads (a "locking read"); SELECT ... FOR SHARE takes a shared lock that allows other readers but blocks writers. Whenever a decision in your program depends on data you read, either do the read and write in one statement, or lock the rows when you read them.

Locks live until COMMIT or ROLLBACK

Locks are held until the transaction ends. Keep transactions short, and never wait for a person (a click, a prompt) inside an open transaction.

06Deadlocks

A deadlock is a circle of waiting: T1 holds a lock that T2 needs, while T2 holds a lock that T1 needs. Neither can ever continue. Databases detect this and break the circle.

Watch one happen

Two transfers touch the same two accounts in opposite order. T1 locks Alice, T2 locks Bob, and then each asks for the other row. Replay the recording:

InnoDB noticed the cycle immediately and rolled back one transaction, the victim. In this recording the victim was T2; the server may choose either one. The victim receives ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction, and its entire transaction has been rolled back. The other transaction then continued and committed. Final balances: Alice 990, Bob 1010 (only the survivor's change remains).

Lock wait timeout is different

If a session simply waits too long for a lock (no cycle), MySQL gives up after innodb_lock_wait_timeout seconds (default 50) with error 1205. In that case only the waiting statement is rolled back, not the whole transaction. You saw error 1205 in the SERIALIZABLE recordings, where the wait was cut to 2 seconds.

How to avoid and handle deadlocks

  • Access rows in a consistent order. If both transfers always lock the lower account id first, the circle cannot form.
  • Keep transactions short and do not hold locks while waiting for users or other systems.
  • Use indexes on the columns you filter by, so you lock fewer rows.
  • Expect them and retry. Even careful code gets an occasional deadlock. The standard remedy is to catch error 1213 and run the whole transaction again:
Python (PyMySQL)
import time, pymysql

DEADLOCK = 1213   # ER_LOCK_DEADLOCK

def run_with_retry(conn, work, attempts=3):
    for attempt in range(1, attempts + 1):
        try:
            work(conn)             # your transaction: statements, then conn.commit()
            return
        except pymysql.MySQLError as e:
            conn.rollback()
            if e.args[0] == DEADLOCK and attempt < attempts:
                time.sleep(0.05 * attempt)   # short pause, then try again
                continue
            raise

07Access control

Security starts with a simple question: who is allowed to do what? A database answers it with accounts and privileges. This section uses real accounts on the server and shows the real error messages you will see when something is not allowed.

The goals

GoalMeaningExample failure
ConfidentialityOnly authorized people can read the data.A clerk reads every employee's salary.
IntegrityOnly authorized people can change the data, and changes are valid.Someone edits a grade or a balance.
AvailabilityAuthorized people can use the data when they need it.A table is dropped, or the server is overwhelmed.

Two steps protect them. Authentication proves who you are (user name and password). Authorization decides what you may do once you are in (privileges). Different things can go wrong in each, so keep them separate in your head.

Create a user

MySQL identifies an account by user name and the host it connects from, written 'ana'@'localhost'. A user that can connect from anywhere is 'ana'@'%'; avoid that unless you need it. A new user can connect but can do almost nothing.

SQL
CREATE USER 'ana'@'localhost' IDENTIFIED BY 'Pass#1234';
SELECT user, host, plugin FROM mysql.user WHERE user = 'ana';
Output (MySQL 8.4)
+------+-----------+-----------------------+
| user | host      | plugin                |
+------+-----------+-----------------------+
| ana  | localhost | caching_sha2_password |
+------+-----------+-----------------------+
1 row in set

Roles: manage privileges for groups

Granting the same ten privileges to fifty users one by one is error-prone. A role is a named bundle of privileges that you grant to users. MySQL 8.0 and later support roles. A granted role is not active until the user switches it on (SET ROLE) or an administrator makes it a default role:

SQL
CREATE ROLE 'reporting';
GRANT SELECT ON tx_demo.* TO 'reporting';
CREATE USER 'rita'@'localhost' IDENTIFIED BY 'Pass#1234';
GRANT 'reporting' TO 'rita'@'localhost';

SELECT CURRENT_ROLE();
SELECT COUNT(*) AS n FROM tx_demo.orders;
SET ROLE 'reporting';
SELECT CURRENT_ROLE();
SELECT COUNT(*) AS n FROM tx_demo.orders;

Habits
  • Never let an application connect as root. Create an account that has only the privileges the application needs (often SELECT, INSERT, UPDATE, DELETE on one database, never DROP or GRANT).
  • GRANT ALL ON *.* is almost never the right answer.
  • Review accounts regularly. Remove accounts that nobody uses.

08SQL injection

SQL injection happens when a program builds an SQL statement by pasting user input into the text. The input is then parsed as SQL, so a user can change what the query does. It has been among the most common and most damaging web vulnerabilities for over twenty years, and it is entirely preventable.

This section is about recognizing and preventing the flaw. The lab and the examples run only against a small, made-up database in your own browser or on the course server; never test anything like this on a system you do not own or have written permission to test. Section 10 explains why.

The vulnerable pattern

Python (what NOT to do)
# DANGEROUS: do not write code like this
sql = "SELECT id, username, role FROM app_user " \
      "WHERE username = '" + username + "' AND password = '" + password + "'"
cursor.execute(sql)

If the user types alice and alicepw the text is fine. But the user controls what goes between the quotes. Here are real runs against MySQL 8.4 (the tables app_user and product hold three made-up users and three products):

Normal login

What the user typed: username = 'alice', password = 'alicepw'

SQL sent to MySQL
SELECT id, username, role FROM app_user WHERE username = 'alice' AND password = 'alicepw'
Result (MySQL 8.4)
2 | alice | user
(1 row)

Wrong password

What the user typed: username = 'alice', password = 'wrong'

(no rows)

What the user typed: username = 'alice', password = "' OR '1'='1"

SELECT id, username, role FROM app_user WHERE username = 'admin'--' AND password = 'x'
Result (MySQL 8.4)
ERROR 1064: You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 'x'' at line 1

Attack 3: stacking a second statement

What the user typed: username = "x'; DROP TABLE app_user; -- ", password = 'y'

SQL sent to MySQL
SELECT id, username, role FROM app_user WHERE username = 'x'; DROP TABLE app_user; -- ' AND password = 'y'
Result (MySQL 8.4)
ERROR 1064: You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near 'DROP TABLE app_user; -- ' AND password = 'y'' at line 1

The table is still there: SELECT COUNT(*) FROM app_user returns 3. MySQL drivers refuse to run more than one statement per call unless you explicitly enable multi-statements, which is why this attack usually fails against MySQL. Other database systems and drivers behave differently, and the first two attacks need no stacking at all, so do not count on this protection.

Attack 4: reading another table with UNION

What the user typed: search = "zzz' UNION SELECT username, password FROM app_user -- "

SQL sent to MySQL
SELECT name, price FROM product WHERE name LIKE '%zzz' UNION SELECT username, password FROM app_user -- %'
Result (MySQL 8.4)
admin | s3cret-admin
alice | alicepw
bob | bobpw
(3 rows)

The same inputs, safely

Now the query text is fixed, and the user's input is passed as parameters. The database never parses the input as SQL, so the quote characters are just characters. Same attack inputs, harmless result:

Safe: attack 1

What the user typed: username = 'alice', password = "' OR '1'='1"

SQL with parameters
SELECT id, username, role FROM app_user WHERE username = alice AND password = ' OR '1'='1
-- parameters: ('alice', "' OR '1'='1")
Result (MySQL 8.4)
(no rows)

Safe: attack 2

What the user typed: username = "admin' -- ", password = 'x'

SQL with parameters
SELECT id, username, role FROM app_user WHERE username = admin' --  AND password = x
-- parameters: ("admin' -- ", 'x')
Result (MySQL 8.4)
(no rows)

Safe: attack 4

What the user typed: search = "zzz' UNION SELECT username, password FROM app_user -- "

SQL with parameters
SELECT name, price FROM product WHERE name LIKE %s
-- parameter: "%zzz' UNION SELECT username, password FROM app_user -- %"
Result (MySQL 8.4)
(no rows)
Why one attack failed

Dialect note. In MySQL a -- comment must be followed by a space (or a control character). That is why the version without the space failed with a syntax error while -- worked. MySQL also accepts # as a comment. The attacker adapts to the database, so never rely on such details as a defense. The browser lab below uses SQLite, where -- works without a space.

Defenses

  1. Parameterized queries (prepared statements). Always. Keep the SQL text fixed and pass values separately. This is the primary defense.
  2. Least privilege. The application account should not be able to DROP tables or read tables it does not need. Then even a successful injection does limited harm (section 7).
  3. Allow-lists for things that cannot be parameters. Table names, column names and ORDER BY directions cannot be bound as parameters. If you must take them from the user, map the input to a fixed list in your code (for example, only name or price).
  4. Validate input for type and length. This is a helpful second layer, not a replacement for parameters.
  5. Do not show raw database errors to users. They reveal table and column names. Log them privately.
  6. Watch for the same mistake in "safe-looking" tools. An ORM or query builder protects you only while you use its parameter features. Building a raw SQL string from user input inside an ORM is still injection.

The same flaw exists in the safe-looking version only if you go back to concatenating strings. The correct code is short:

Python (PyMySQL)
# SAFE: the values travel as parameters, not as SQL text
cursor.execute(
    "SELECT id, username, role FROM app_user WHERE username = %s AND password = %s",
    (username, password))

In Java use PreparedStatement with ? placeholders and setString (Module 8). The principle is identical in every language.

09Protecting the data

Access control decides who may ask. These measures protect the data itself, in case someone gets past the front door or the hardware is lost.

Never store passwords as text

If your database stores passwords in a plain column, then anyone who reads that table (an attacker, a careless administrator, a leaked backup) has every user's password, and people reuse passwords on other sites. The correct approach is to store only a salted, slow hash of each password:

  • A hash is a one-way function: you can compute it from the password but not reverse it.
  • A salt is a random value, different for each user, stored next to the hash. It makes two users with the same password have different hashes, and it defeats precomputed tables.
  • The hash must be deliberately slow and memory-hungry, so guessing millions of passwords is expensive. Use a password hashing function: Argon2id, scrypt, bcrypt or PBKDF2. Fast general hashes such as plain SHA-256 are the wrong tool for passwords.

OWASP's Password Storage Cheat Sheet recommends Argon2id where it is available, with scrypt, bcrypt and PBKDF2 as alternatives; follow its current parameter advice in real systems. Use a maintained library and never invent your own scheme. This demonstration uses scrypt from Python's standard library, with fixed salts so the output is reproducible (a real salt is random, at least 16 bytes, from os.urandom or secrets):

Python
import hashlib, hmac

def hash_password(password, salt):
    return hashlib.scrypt(password.encode(), salt=salt, n=2**14, r=8, p=1, dklen=32)

def verify(password, salt, stored):
    return hmac.compare_digest(hash_password(password, salt), stored)   # constant-time compare
Output (Python, scrypt)
same password, salt 1:  e6dd06aff1606492483ad13d855548716f8b74a60bfe31523a4b4c6aec0db114
same password, salt 2:  4339d347dce9b8c014fcb65309604002dd96749e40a29f534c1167c32994e11a
verify("correct horse"): True
verify("wrong horse"):   False

The same password produced two completely different stored values. The parameters here (n=2**14) are chosen to keep the demonstration fast; production systems need stronger settings. A typical table has columns username, salt and password_hash; there is never a column called password that holds the real thing.

Defense in depth

No single control is enough. A realistic system stacks them: parameterized queries so injection fails, least privilege so a failure does little harm, hashed passwords so a leak does not reveal secrets, encryption and backups so loss does not end the business, and logging so you notice. Each layer assumes the one before it might fail.

10Ethics and the law

People who work with databases hold other people's grades, health records, finances and private messages. The technology gives you power; ethics and law set the limits on how you may use it.

Not legal advice

This section is general education, not legal advice. Laws differ by country, state and industry, and they change. When a real situation involves legal risk, involve your organization's legal counsel.

A small toolbox for hard questions

  • Authorization is not the same as permission. What the system lets you do and what you are entitled to do are different.
  • Purpose. Was this data collected for this use? Would the people it describes expect it?
  • Minimize. Do you need the data at all, and for how long?
  • Be accountable. Assume your actions will be logged and read aloud later. Could you defend them?
  • Professional codes. The ACM Code of Ethics and Professional Conduct is a good reference for computing professionals.

Six cases

For each case, decide what you would do before you open the discussion.

Case 1: A curious administrator

You are the database administrator at a hospital. You have full access. A famous local athlete is admitted, and you wonder what is wrong with them. Nobody would ever know if you looked at the record. What do you do?

What should you do? Think first, then open.

Do not look. Having the technical ability is not permission. Access rights are granted for a purpose (running the system), and looking at a record without a work reason is a breach of confidentiality and of the organization's policy, even if no harm follows. In many places it also breaks the law (for health records in the United States, HIPAA's privacy rules). Good systems log and audit access precisely so that curiosity is detectable.

ACM Code of Ethics: 1.6 Respect privacy; 1.7 Honor confidentiality; 2.8 Access computing and communication resources only when authorized.

Case 2: A hole in someone else's website

While browsing an online shop you notice that a search box shows a database error when you type an apostrophe. You suspect SQL injection. You are curious to see how far it goes. What do you do?

What should you do? Think first, then open.

Stop and report it; do not exploit it. Testing a system you do not own without written permission can be illegal, even with good intentions (in the United States, for example, the Computer Fraud and Abuse Act prohibits unauthorized access). Responsible practice is to stop, do not copy or view any data, and tell the organization through its security contact or a published disclosure policy. Many organizations publish a vulnerability disclosure program that sets out what is permitted.

Practice on your own systems or on training environments built for the purpose, as in this tutorial.

Case 3: Real data for testing

To test a new report, a colleague copies the production customer table, with real names and emails, to their laptop and a shared test server. Is that acceptable?

What should you do? Think first, then open.

Not as described. Production personal data should not leave its protected environment for convenience. Use synthetic data (like the made-up tables in this course) or mask and anonymize real data first, and apply the same access controls to any copy that must exist. The principles of data minimization and purpose limitation (data collected for one purpose is not freely reusable for another) are part of laws such as the EU's GDPR.

Case 4: A breach

You discover that an attacker downloaded the customer table of your company's service six weeks ago. A manager suggests saying nothing until the investigation is complete, to avoid bad publicity. What are your obligations?

What should you do? Think first, then open.

Escalate to the people responsible for legal and security response immediately, and do not hide it. Many laws require notification. For example, the EU's GDPR generally requires a controller to notify the supervisory authority without undue delay and, where feasible, within 72 hours of becoming aware of a personal data breach, and to tell affected people when the risk to them is high. US states have their own breach-notification laws, and sector rules such as HIPAA add specific requirements. Delay and concealment usually make the legal and ethical position much worse. Details depend on place and situation, so this is where you involve legal counsel.

Case 5: Student records

You maintain the system that holds student grades. A parent calls, says they are paying the tuition, and asks you to read out their adult child's grades. What do you do?

What should you do? Think first, then open.

Do not disclose. In the United States, FERPA gives students (once they are 18 or attend a postsecondary institution) control over their education records, and disclosure generally needs the student's consent, with specific exceptions. The right action is to follow your institution's policy, which usually means referring the parent to the student or the registrar. The wider lesson: authentication of the person asking, and a rule about who may receive what, come before helpfulness.

Case 6: Delete my data

A user from the EU asks your company to delete all of their personal data. Your data is also inside nightly backups that are kept for 30 days. What should a well-designed system do?

What should you do? Think first, then open.

Plan for it from the start. GDPR gives individuals a right to erasure in many circumstances (Article 17), with exceptions. In practice that means knowing where personal data lives, being able to remove it from live systems, and having a documented approach for backups, for example letting them expire on schedule and not restoring deleted people's data. This is a design requirement, not something to improvise after the request arrives.
