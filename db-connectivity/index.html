1. Connect to a database

Say what a driver does, build a connection URL, and open and close a connection safely in Java and Python.

Theory

The five steps every program follows

  1. Connect: open a session with the database, giving it a location and credentials.
  2. Create a statement or cursor: the object that carries SQL to the server.
  3. Execute the SQL.
  4. Process the result: rows for a SELECT, a row count for an INSERT, UPDATE, or DELETE.
  5. Close everything you opened, even when an error happens.

You do not write the network code yourself. A driver translates your calls into the database's own protocol. Java standardizes the calls as JDBC (java.sql), and Python standardizes them as the DB-API 2.0 (PEP 249). Because the shape is standard, code for MySQL looks almost the same as code for PostgreSQL. Only the driver, the connection details, and the SQL dialect change.

SQLite is the odd one out, which makes it ideal for learning. It has no server. The "database" is a file (or memory) opened by a library inside your own program, so there is no host, port, or password. Everything else in this tutorial works the same way.

Python first. This lab uses only the standard library, so you can run it right now.

Lab 0: lab0_hello.pyRun here
import sqlite3

# 1. Connect. SQLite needs no server: ":memory:" is a database that lives inside this program.
conn = sqlite3.connect(":memory:")
print("connected, SQLite version", sqlite3.sqlite_version)

# 2. Get a cursor, the object that sends statements and holds results.
cur = conn.cursor()

# 3. Execute statements.
cur.execute("CREATE TABLE greeting (id INTEGER PRIMARY KEY, text TEXT)")
cur.execute("INSERT INTO greeting (text) VALUES (?)", ("Hello, database!",))
conn.commit()

# 4. Process the result.
cur.execute("SELECT id, text FROM greeting")
print(cur.fetchone())

# 5. Close what you opened.
cur.close()
conn.close()
print("closed")

Now Java. The connection is a try-with-resources resource, so it is closed automatically when the block ends, even after an exception.

ConnectDemo.javaCompiled only
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;

public class ConnectDemo {
    public static void main(String[] args) {
        // jdbc:<subprotocol>://<host>:<port>/<database>?<options>
        String url  = "jdbc:mysql://localhost:3306/school";
        String user = System.getenv("DB_USER");
        String pass = System.getenv("DB_PASS");

        // No Class.forName(...) needed: a JDBC 4+ driver jar on the classpath registers itself.
        try (Connection conn = DriverManager.getConnection(url, user, pass)) {
            System.out.println("Connected: " + conn.getMetaData().getDatabaseProductName()
                    + " " + conn.getMetaData().getDatabaseProductVersion());
        } catch (SQLException e) {
            System.err.println("Could not connect: " + e.getMessage());
        }   // the connection is closed here, even if an exception was thrown
    }
}

Credentials

Never put a password in source code

Both examples read the user and password from environment variables. Source files get copied, committed to GitHub, and pasted into chat. 2. Run queries and read result sets

Execute SELECT, INSERT, UPDATE, and DELETE from code, walk the rows that come back, and control when changes become permanent.

Theory

A result set is not a list. It is a cursor that moves through rows the server is still delivering. A JDBC ResultSet starts before the first row, so you must call next() once before reading anything. Try it:

Transactions

Nothing is permanent until you commit

A transaction groups statements so they all take effect or none do. This is where the languages differ, and where beginners get bitten:

  • Python DB-API: a transaction is opened for you; changes are invisible to others until conn.commit(). In sqlite3, with conn: commits when the block succeeds and rolls back when it raises (it does not close the connection).
  • JDBC: every statement is committed immediately (auto-commit is on). For a multi-statement transaction call conn.setAutoCommit(false), then commit() or rollback().

Lab 1 proves it with two connections: a second "user" sees 4 rows before the commit and 5 after.

Lab 1: lab1_basics.pyRun here
import sqlite3

DB = "school.db"          # a file in the current folder; use ":memory:" for a throwaway database

# ---- 1. Connect --------------------------------------------------------------
conn = sqlite3.connect(DB)            # creates the file if it does not exist
conn.execute("PRAGMA foreign_keys = ON")

# ---- 2. Create and load (a "with conn" block commits on success, rolls back on error) ----
with conn:
    conn.execute("DROP TABLE IF EXISTS student")
    conn.execute("""
        CREATE TABLE student (
            sid   INTEGER PRIMARY KEY,
            name  TEXT NOT NULL,
            major TEXT,
            gpa   REAL,
            phone TEXT
        )""")
    conn.executemany("INSERT INTO student VALUES (?, ?, ?, ?, ?)", [
        (1, "Ada Lovelace", "Computer Science", 3.9, "555-0101"),
        (2, "Ben Carter",   "Mathematics",      3.4, None),
        (3, "Carla Diaz",   "Computer Science", 3.7, "555-0103"),
        (4, "Dev Patel",    "Data Science",     3.2, None),
    ])

# ---- 3. Query and walk the result set ----------------------------------------
cur = conn.execute(
    "SELECT sid, name, gpa FROM student WHERE major = ? ORDER BY sid", ("Computer Science",))
print("columns:", [d[0] for d in cur.description])
for row in cur:                        # a cursor is iterable: one tuple per row
    print(row)

cur = conn.execute("SELECT sid, name FROM student ORDER BY sid")
print("fetchone:", cur.fetchone())             # the next single row
print("fetchall:", cur.fetchall())             # every remaining row, as a list
print("fetchone again:", cur.fetchone())       # None once the rows are used up

# ---- 4. Access columns by name, and meet NULL --------------------------------
conn.row_factory = sqlite3.Row
for row in conn.execute("SELECT name, phone FROM student ORDER BY sid"):
    print(row["name"], "->", row["phone"])    # a NULL value arrives as None
conn.row_factory = None

# ---- 5. One value, and how many rows an UPDATE changed -----------------------
print("students:", conn.execute("SELECT COUNT(*) FROM student").fetchone()[0])
with conn:
    cur = conn.execute("UPDATE student SET gpa = gpa + 0.1 WHERE major = ?", ("Data Science",))
    print("rows updated:", cur.rowcount)

# ---- 6. Transactions: nothing is permanent until commit ----------------------
conn.execute("INSERT INTO student VALUES (5, 'Eve Stone', 'Mathematics', 3.5, NULL)")
other = sqlite3.connect(DB)            # a second connection, like a second user
print("before commit, the other user sees:", other.execute("SELECT COUNT(*) FROM student").fetchone()[0])
other.close()
conn.commit()
other = sqlite3.connect(DB)
print("after commit, the other user sees:", other.execute("SELECT COUNT(*) FROM student").fetchone()[0])
other.close()

# ---- 7. A failed transaction is undone ---------------------------------------
try:
    with conn:
        conn.execute("INSERT INTO student VALUES (6, 'Fay Wu', 'Data Science', 3.8, NULL)")
        conn.execute("INSERT INTO student VALUES (1, 'Duplicate', 'None', 0.0, NULL)")   # sid 1 already exists
except sqlite3.IntegrityError as e:
    print("error:", e)
print("students after the failed block:", conn.execute("SELECT COUNT(*) FROM student").fetchone()[0])

conn.close()                           # always release the connection when you are done

The same work in Java, against MySQL. Read the structure rather than every line: a query, a loop on rs.next(), and an update that reports its row count.

StudentApp.javaCompiled only
import java.sql.*;

public class StudentApp {
    // Credentials come from environment variables, never from source code.
    static final String URL  = System.getenv().getOrDefault("DB_URL",
            "jdbc:mysql://localhost:3306/school?useSSL=false&allowPublicKeyRetrieval=true");
    static final String USER = System.getenv().getOrDefault("DB_USER", "app_user");
    static final String PASS = System.getenv().getOrDefault("DB_PASS", "change_me");

    public static void main(String[] args) {
        // try-with-resources closes Connection, PreparedStatement and ResultSet automatically
        try (Connection conn = DriverManager.getConnection(URL, USER, PASS)) {
            System.out.println("Connected to " + conn.getMetaData().getDatabaseProductName());

            String sql = "SELECT sid, name, gpa FROM student WHERE major = ? AND gpa >= ? ORDER BY sid";
            try (PreparedStatement ps = conn.prepareStatement(sql)) {
                ps.setString(1, "Computer Science");   // placeholders are numbered from 1
                ps.setDouble(2, 3.5);
                try (ResultSet rs = ps.executeQuery()) {
                    while (rs.next()) {                 // moves the cursor; false when rows run out
                        int sid = rs.getInt("sid");
                        String name = rs.getString("name");
                        double gpa = rs.getDouble("gpa");
                        System.out.printf("%d  %s  %.2f%n", sid, name, gpa);
                    }
                }
            }

            String upd = "UPDATE student SET gpa = ? WHERE sid = ?";
            try (PreparedStatement ps = conn.prepareStatement(upd)) {
                ps.setDouble(1, 3.95);
                ps.setInt(2, 1);
                System.out.println("rows updated: " + ps.executeUpdate());
            }
        } catch (SQLException e) {
            System.err.println("SQLState=" + e.getSQLState() + " code=" + e.getErrorCode() + " " + e.getMessage());
        }
    }
}

Do not fetch everything by habit. fetchall() loads every row into memory at once. That is fine for 4 rows and a problem for 40 million. Iterate over the cursor, use fetchmany(n), or add a LIMIT. Also name your columns in the SELECT instead of using SELECT *, so adding a column later cannot break your positional indexes.

3. Parameterized queries and SQL injection

See exactly how pasting user input into SQL lets an attacker rewrite your query, then fix it with parameters.

Theory

When data becomes code

A SQL statement is a program. If you build it by joining strings, whatever the user types becomes part of that program. Here is a login check written the dangerous way:

sql = f"SELECT username, role FROM users WHERE username = '{username}' AND password = '{password}'"

A user who types ' OR '1'='1' -- as the username changes what the query means:

  1. The leading ' closes the string early.
  2. OR '1'='1' adds a condition that is always true.
  3. -- starts a comment, which silently removes the password check.

The same hole lets an attacker read other tables (UNION SELECT) or, on drivers that allow several statements in one call, change data. Lab 2 shows all of these on real queries.

The fix is a different channel, not better quoting. With a parameterized query (also called a prepared statement) the SQL text goes to the database with placeholders, and the values travel separately. The database finishes parsing the statement before it sees the values, so a value can never turn into SQL. An apostrophe in the value is just an apostrophe.

# ===================== Part 1: login =====================
def login_vulnerable(username, password):
    # DANGER: user input is pasted into the SQL text
    sql = f"SELECT username, role FROM users WHERE username = '{username}' AND password = '{password}'"
    print("   SQL sent  :", sql)
    try:
        return conn.execute(sql).fetchone()
    except sqlite3.Error as e:
        return f"ERROR: {e}"


def login_safe(username, password):
    # SAFE: the SQL text is fixed; the values travel separately as parameters
    sql = "SELECT username, role FROM users WHERE username = ? AND password = ?"
    return conn.execute(sql, (username, password)).fetchone()


attempts = [

Read the output closely:

  • Two attacks log in without a valid password: the first as the first user in the table, the second as the administrator.
  • The honest user "O'Brien" breaks the vulnerable function with a syntax error. Injection bugs are also ordinary bugs: any name with an apostrophe crashes the page. The safe function simply finds no such user.

Java

The same fix in JDBC

Replace Statement with PreparedStatement, put ? where each value goes, and bind values by position starting at 1.

SafeLogin.javaCompiled only
import java.sql.*;

public class SafeLogin {
    // VULNERABLE: the input becomes part of the SQL text
    static boolean loginBad(Connection c, String user, String pass) throws SQLException {
        String sql = "SELECT 1 FROM users WHERE username = '" + user + "' AND password = '" + pass + "'";
        try (Statement st = c.createStatement(); ResultSet rs = st.executeQuery(sql)) {
            return rs.next();
        }
    }

    // SAFE: fixed SQL text, values sent separately
    static boolean loginGood(Connection c, String user, String pass) throws SQLException {
        String sql = "SELECT 1 FROM users WHERE username = ? AND password = ?";
        try (PreparedStatement ps = c.prepareStatement(sql)) {
            ps.setString(1, user);
            ps.setString(2, pass);
            try (ResultSet rs = ps.executeQuery()) {
                return rs.next();
            }
        }
    }

    // A placeholder cannot hold a column name, so check against a fixed list
    static String sortColumn(String requested) {
        switch (requested) {
            case "name": case "price": return requested;
            default: throw new IllegalArgumentException("bad sort column");
        }
    }
}
Beyond the basics

What placeholders can and cannot do

Lab 3 covers the situations that come up the moment you build a real search page.

  • Names, not values. A placeholder stands for a value. It cannot be a table name, a column name, or ASC/DESC. For "sort by a column the user chose", compare the choice against a fixed allowlist (Lab 2, part 3), then insert the checked name.
  • IN lists. Build the string of placeholders (?,?,?) from the list's length, never the values.
  • LIKE wildcards. A % or _ typed by the user is still a wildcard inside a parameter. It is not an injection, but a user can match more than they should. Escape it if you mean it literally.
  • Optional filters. Add fixed SQL fragments ("major = ?") and collect the values in a separate list.
  • Named parameters. sqlite3 also accepts :name with a dictionary, which reads better with many values.
Lab 3: lab3_dynamic.pyRun here
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE student (sid INTEGER PRIMARY KEY, name TEXT, major TEXT, gpa REAL, note TEXT)")
conn.executemany(
    "INSERT INTO student VALUES (:sid, :name, :major, :gpa, :note)",      # named style: a dict per row
    [
        {"sid": 1, "name": "Ada",   "major": "Computer Science", "gpa": 3.9, "note": "100% attendance"},
        {"sid": 2, "name": "Ben",   "major": "Mathematics",      "gpa": 3.4, "note": "1000 volunteer hours"},
        {"sid": 3, "name": "Carla", "major": "Computer Science", "gpa": 3.7, "note": None},
        {"sid": 4, "name": "Dev",   "major": "Data Science",     "gpa": 3.2, "note": None},
        {"sid": 5, "name": "Eve",   "major": "Mathematics",      "gpa": 3.5, "note": None},
    ],
)

# ---- 1. Named parameters ---------------------------------------------------------
rows = conn.execute(
    "SELECT name FROM student WHERE major = :major AND gpa >= :min_gpa ORDER BY sid",
    {"major": "Computer Science", "min_gpa": 3.7}).fetchall()
print("named:", rows)

# ---- 2. An IN (...) list: build the placeholders, never the values ---------------
ids = [1, 3, 5]
placeholders = ",".join("?" * len(ids))                    # "?,?,?"
sql = f"SELECT name FROM student WHERE sid IN ({placeholders}) ORDER BY sid"
print("IN:", sql, "->", conn.execute(sql, ids).fetchall())

# ---- 3. LIKE: a % or _ typed by the user still acts as a wildcard ----------------
def escape_like(text):
    return text.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_")

term = "100%"
naive = conn.execute("SELECT name FROM student WHERE note LIKE ?", (f"%{term}%",)).fetchall()
exact = conn.execute("SELECT name FROM student WHERE note LIKE ? ESCAPE '\\'",
                     (f"%{escape_like(term)}%",)).fetchall()
print("naive LIKE :", naive, " <- also matches '1000 volunteer hours'")
print("escaped LIKE:", exact)

# ---- 4. Optional filters: append fixed fragments, collect values separately ------
def search(major=None, min_gpa=None):
    conditions, params = [], []
    if major is not None:
        conditions.append("major = ?")
        params.append(major)
    if min_gpa is not None:
        conditions.append("gpa >= ?")
        params.append(min_gpa)
    where = (" WHERE " + " AND ".join(conditions)) if conditions else ""
    return conn.execute("SELECT name FROM student" + where + " ORDER BY sid", params).fetchall()

print("no filters   :", search())
print("major only   :", search(major="Mathematics"))
print("both filters :", search(major="Mathematics", min_gpa=3.5))

# ---- 5. Bulk update: executemany -------------------------------------------------
cur = conn.executemany("UPDATE student SET note = ? WHERE sid = ?",
                       [("dean's list", 1), ("dean's list", 3)])
print("rows changed by executemany:", cur.rowcount)

# ---- 6. Three mistakes you will meet, and their real error messages --------------
mistakes = [
    ("single value not in a tuple",
     lambda: conn.execute("SELECT * FROM student WHERE major = ?", "Computer Science")),
    ("too few values",
     lambda: conn.execute("SELECT * FROM student WHERE major = ? AND gpa > ?", ("Mathematics",))),
    ("wrong table name",
     lambda: conn.execute("SELECT * FROM students")),
]
for label, attempt in mistakes:
    try:
        attempt()
    except sqlite3.Error as e:
        print(f"{label}: {type(e).__name__}: {e}")
print("the fix for the first one: pass a tuple with a trailing comma, e.g. (major,)")

too few values: ProgrammingError: Incorrect number of bindings supplied. The current statement uses 2, and there are 1 supplied.
wrong table name: OperationalError: no such table: students
the fix for the first one: pass a tuple with a trailing comma, e.g. (major,)
Defense in depth

Parameters first, then the safety nets

  • Least privilege. The application's database account should not be able to DROP tables or read tables it does not use. If an injection slips through, the damage is capped.
  • Validate input for sanity (length, format), as a second layer. It is not a substitute for parameters.
  • Do not show raw database errors to users. They reveal table and column names. Log them privately instead.
  • Do not hand-escape quotes. Replacing ' with '' is easy to get wrong across encodings and contexts. Let the driver do it by using parameters.
MySQL detail. MySQL requires a space after -- for it to start a comment (-- ), and also accepts #. The simulator and Lab 2 run on SQLite, where -- alone works. The attack idea is identical; the exact characters vary by database.

Driver comparison

The placeholder trap. sqlite3 uses ?. mysql.connector and psycopg2 use %s. That %s is the driver's placeholder, not Python string formatting. Writing "... WHERE id = %s" % user_id with the % operator is the vulnerable pattern wearing the safe pattern's clothes. The safe call has a comma: cur.execute(sql, (user_id,)).

    cur = conn.cursor()
    # mysql.connector uses %s as the placeholder (it is NOT Python string formatting)
    cur.execute("SELECT sid, name, gpa FROM student WHERE major = %s AND gpa >= %s ORDER BY sid",
                ("Computer Science", 3.5))
    for sid, name, gpa in cur.fetchall():
        print(sid, name, gpa)

    cur.execute("UPDATE student SET gpa = %s WHERE sid = %s", (3.95, 1))
    print("rows updated:", cur.rowcount)
    conn.commit()                      # connectors for MySQL do not auto-commit by default
finally:
    conn.close()

Beyond one connection

Raw SQL, pools, and ORMs

ApproachWhat it isChoose it whenWatch out for
Plain driver (JDBC, DB-API)You write SQL and manage the connection.Scripts, coursework, small tools, and anywhere you need full control of the SQL.Boilerplate, and the temptation to build SQL with strings.
Connection pool (HikariCP, SQLAlchemy's pool)A set of already-open connections that your code borrows and returns.Any server handling many requests. Opening a connection is slow and databases limit how many they accept.You must always return the connection (close it in a finally or try-with-resources, which returns it to the pool).
ORM (JPA/Hibernate, SQLAlchemy ORM)Maps tables to classes and generates SQL for you.Large applications with many tables and mostly standard create, read, update, delete operations.Generated SQL can be inefficient (the "N+1 query" problem), and it hides what actually runs. It is still safe only if you do not splice strings into raw fragments.

An ORM is a layer on top of a driver, not a replacement for one, and a pool sits between the two. Knowing the plain driver is what lets you debug the layers above it.

SQL is still not fully portable. The API is standard, but dialects differ: LIMIT versus FETCH FIRST, auto-increment syntax, date functions, and string quoting. An ORM can smooth some of this over. Raw SQL cannot.

Apply it

Capstone: a command-line grade book

Build a small program, in Python (use sqlite3) or Java (JDBC with MySQL), that manages a course's grades. It needs three tables: student, course, and enrollment (student, course, grade).

  1. Connect using settings from environment variables or a function argument, never hard-coded credentials. Close the connection even if something fails.
  2. Create the schema with primary keys, a foreign key from enrollment to each of the other tables, and a CHECK that a grade is between 0 and 100.
  3. Add a student, a course, and an enrollment through functions that take parameters.
  4. Report: list a course's students with grades, highest first, and print each student's average. Handle the case where a student has no grades (NULL).
  5. Search students by part of a name using LIKE, with the user's text passed as a parameter.
  6. Record grades in one transaction: adding five grades must succeed or fail together. Prove it by making the fourth grade invalid and checking that none were saved.
  7. Attack it. Try ' OR '1'='1, an apostrophe name, and a % search. Write one sentence for each saying what happened and why.

Self-check: no SQL string anywhere contains an f-string brace or a + that joins user input. If you have one, that is the bug.
