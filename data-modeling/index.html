01Models and levels

A data model is a way of describing data: what things exist, what is known about them, how they relate, and what rules the data must obey. Before you can write a single CREATE TABLE you need a model. This module takes you from an idea in the real world to a working relational schema.

Three levels of modeling

Designers work from the general to the specific. Each level answers a different question and uses a different notation.

LevelQuestion it answersTypical notationExample
ConceptualWhat things matter, and how do they relate? Independent of any database product.ER or EER diagramStudent, Course, Department; a student enrolls in many courses.
LogicalHow is it organized in the chosen kind of database (here, the relational model)?Relational schema: tables, columns, keysstudent(sid, name, dept_id) with dept_id referring to department.
PhysicalHow is it stored in a specific product, for speed and space?DDL for one product, plus indexes, types, storage engineCREATE TABLE ... ENGINE=InnoDB in MySQL 8.4.

Earlier tutorials covered the conceptual level (ER and EER modeling). This one covers the relational model itself and the mapping from the conceptual level down to the logical and physical levels. Normalization then tells you how to judge whether the logical design is a good one.

Why the relational model?

Proposed by E. F. Codd in 1970, the relational model describes all data as relations: tables of values. It rests on mathematics (sets and logic, the subject of Module 3), which is why a database can reason about your queries and optimize them. Other models exist and are covered in Module 5 (key-value, document, graph), and each is best for some jobs, but the relational model remains the default for structured business data.

02The relational model

The relational model has its own vocabulary. SQL uses different everyday words for the same ideas, so learn both.

Vocabulary

Formal termIn SQL and everyday useMeaning
RelationTableA set of tuples that all have the same attributes.
TupleRow, recordOne fact: a list of values, one per attribute.
AttributeColumn, fieldA named property with a domain.
DomainData type plus allowed valuesThe set of values an attribute may take (for example whole numbers, or GPAs from 0 to 4).
DegreeNumber of columnsThe number of attributes of a relation.
CardinalityNumber of rowsThe number of tuples in a relation right now. (This word also has a different meaning in ER diagrams: 1:N.)
Relation schemaTable definitionThe relation name and its attributes with domains, for example student(sid, name, email, dept_id, gpa).
Relation instanceThe rows currently storedThe set of tuples at a particular moment. It changes all the time; the schema rarely does.

Schema versus instance

This distinction runs through the whole course. The schema is the design: it says what can be stored and which rules apply. The instance is the data that is stored at this moment. You design schemas; users fill instances. A rule belongs in the schema (a constraint), never in the hope that the current rows happen to follow it.

What a relation is (and is not)

In the formal model a relation is a set of tuples, which has consequences:

  • No duplicate tuples. Two identical rows would be the same tuple. SQL tables can contain duplicate rows unless a key forbids it, which is one more reason every table needs a primary key.
  • No row order. A table has no first row. Without ORDER BY, a query may return rows in any order.
  • No column order in the formal model, although SQL does remember the order the columns were declared in.
  • Atomic values. Each cell holds a single value, not a list. This is first normal form (Module 7).
  • NULL means "no value is known or applicable". It is not zero and not an empty string, and it is not a value of any domain. Section 4 shows how constraints treat it.

A relation is not a file or an array

Programs often hold records in arrays or files, where position matters and duplicates are fine. Relations are different: you refer to data by values (keys), never by position. That is what makes it possible to reorganize storage without breaking programs, an idea covered in Module 1 as data independence.

03Keys

Keys are how the relational model identifies tuples and connects relations. Everything else (joins, foreign keys, indexes) builds on them.

The kinds of key

KeyDefinition
SuperkeyA set of attributes whose values are different for every tuple, in every legal instance. Adding more attributes to a superkey gives another superkey.
Candidate keyA minimal superkey: remove any attribute and it stops being unique. A relation can have several.
Primary keyThe candidate key the designer picks to identify tuples. It can never be NULL. One per table.
Alternate keyA candidate key that was not chosen as the primary key. Enforce it with UNIQUE.
Foreign keyAttributes in one relation whose values must match the primary (or a unique) key of another relation, or be NULL. It creates the link between tables.
Composite keyA key made of more than one attribute, such as (sid, cid) in enrolled.

A key is a rule, not an observation

You cannot find out the key by looking at the data. Data can only disprove a candidate key (two rows share the values), never prove it. If every name in your table happens to be different today, that does not make name a key, because tomorrow two people called Alex Kim may enroll. The key comes from the rules of the real world you are modeling: "every student has a unique id", "a flight number is reused every day, so it needs the date".

Key explorer

Pick a table, tick some attributes, and see whether the values are unique in the rows shown. Then look at the list of attribute sets that could be keys. Notice how many sets the current data allows that no sensible designer would choose.

The explorer checks uniqueness on these particular rows, which is exactly the "can only disprove" situation described above. The results were checked against MySQL (COUNT(DISTINCT ...) for every attribute set of every table).

Choosing a primary key

  • Stable. It should never change. An email address or a name changes; a generated id does not.
  • Never NULL, always unique. Required by definition.
  • Small. Foreign keys copy it into other tables, and it is stored in every index, so a short integer beats a long text.
  • Meaningless is fine. A surrogate key (a generated number such as sid or an AUTO_INCREMENT column) has no business meaning and therefore no reason to change. A natural key comes from the data (such as an ISBN). Use natural keys only when they are truly stable and unique, and still consider adding a UNIQUE constraint on them if you pick a surrogate.

04Integrity constraints

Integrity constraints are the rules the database enforces for you, on every insert, update and delete, no matter which program is talking to it. They are the main reason to use a database instead of a pile of files.

The four kinds

ConstraintRuleMySQL feature
DomainEvery value must belong to its attribute's domain.Data type, NOT NULL, CHECK, DEFAULT
KeyNo two tuples may have the same key value.PRIMARY KEY, UNIQUE
Entity integrityNo primary key attribute may be NULL.Implied by PRIMARY KEY
Referential integrityA foreign key must match an existing row in the referenced table, or be NULL.FOREIGN KEY ... REFERENCES, with ON DELETE / ON UPDATE actions

Try to break the rules

Fifteen operations on the m2_demo database. Each one was run on a real MySQL 8.4 server, starting from a fresh copy of the data, and its exact response was recorded. Pick one, decide first whether it will succeed, then look.

What the experiments teach

  • Error messages name the constraint. Read them: student.PRIMARY, student.email, fk_student_dept, gpa_range. Giving constraints good names makes errors much easier to understand.
  • NULL passes a foreign key. A student with no department (dept_id NULL) is allowed. If every student must have a department, declare the column NOT NULL too.
  • NULL passes a CHECK. A CHECK that evaluates to unknown (because of NULL) is not a violation. A missing GPA was accepted. Add NOT NULL if a value is mandatory.
  • An empty string is not NULL. NOT NULL accepted '' as a name. If an empty name is invalid, add a CHECK (name <> '').
  • Referential actions decide what happens to children. The default (RESTRICT) refused to delete a department that students belong to. ON DELETE CASCADE on enrolled.sid deleted the student's enrollments along with the student.

Referential actions

ActionWhen a parent row is deleted or its key changes
RESTRICT / NO ACTION (default in MySQL)The operation is refused while child rows exist.
CASCADEThe change is applied to the child rows too (delete them, or update their copy of the key).
SET NULLThe child's foreign key is set to NULL (the column must allow NULL).

MySQL also accepts SET DEFAULT in the syntax but InnoDB rejects it, so do not use it.

05From ER to tables

Turning an ER diagram into tables follows a small set of rules. Learn the rules and the conversion becomes mechanical. Pick a situation below and see the rule and the SQL, which was run on MySQL to make sure it works.

Rule by rule

The whole procedure

  1. Each strong entity set becomes a table. Simple attributes become columns; the entity's key becomes the primary key. For a composite attribute (like an address), keep only its simple parts as columns.
  2. Each weak entity set becomes a table whose primary key is the owner's key plus its partial key.
  3. Each 1:N relationship becomes a foreign key on the N side. Relationship attributes move there too.
  4. Each 1:1 relationship becomes a unique foreign key on one side (preferably the side with total participation).
  5. Each M:N relationship becomes a junction table with a composite primary key of the two foreign keys, plus any relationship attributes.
  6. Each multivalued attribute becomes a table of its own.
  7. Each higher-degree relationship (three or more entities) becomes a junction table with a foreign key to each entity.
  8. Each specialization becomes tables by one of several strategies; choose with the constraints (disjoint or overlapping, total or partial) in mind.
Participation and NULL

Participation tells you about NULL. Total participation (every student must belong to a department) means the foreign key column should be NOT NULL. Partial participation means NULL is allowed.

Worked example

Requirement: "Students belong to one department. Students enroll in many courses, and the grade belongs to the enrollment. A department has many students." From the rules: department and student are strong entities; belongs to is 1:N, so student.dept_id is a foreign key; enrolls in is M:N with a grade attribute, so enrolled(sid, cid, grade) is a junction table. That is exactly the m2_demo schema. Look at the result in MySQL:

SQL
SHOW CREATE TABLE enrolled\G

06From tables to MySQL

The physical design is the same logical schema, written for one product and tuned for it. In MySQL that means choosing data types, constraints, a storage engine and indexes.

Data types: choose the smallest that is correct

NeedGood MySQL typeNotes
Whole numbersINT (4 bytes), BIGINT (8 bytes), SMALLINT, TINYINTUse BIGINT only when you really expect more than about 2 billion rows or values.
Money and exact decimalsDECIMAL(p, s)Exact. Never use FLOAT or DOUBLE for money; they are approximate.
Short textVARCHAR(n)Length is in characters. Pick a realistic maximum.
Long textTEXTCannot be fully indexed without a prefix length.
Dates and timesDATE, DATETIME, TIMESTAMPNever store dates as text.
Yes or noBOOLEAN (an alias for TINYINT(1))MySQL has no separate boolean storage type.

From logical to physical: a checklist

  1. Pick a data type for every column.
  2. Mark mandatory columns NOT NULL.
  3. Declare primary keys, UNIQUE alternate keys and foreign keys, and give constraints meaningful names.
  4. Add CHECK constraints for simple domain rules.
  5. Use the InnoDB engine (the default in MySQL 8.4), which supports transactions and foreign keys.
  6. Choose indexes for the queries you expect (Module 9). Primary key, UNIQUE and foreign key columns are indexed for you.
  7. Choose a naming convention and stick to it (for example lower-case with underscores: dept_id).
